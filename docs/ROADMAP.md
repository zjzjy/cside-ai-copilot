# CSide 开发计划（路线图）

> 更新时间：2026-10-16
> 起点：V1（MVP）已跑通——扩展 → 后端 RAG + LLM → PostgreSQL 落库，52 项自动化测试通过。
> 说明：本文把「已经想清楚下一步做什么」写下来，避免迭代二又变成一次从零讨论。每条都带验收标准，方便直接转成任务卡。

---

## 一、当前基线（V1 已完成）

| 维度 | 现状 |
| --- | --- |
| 产品链路 | 选中客户消息 → 侧边栏生成五步建议（意图 / 策略 / 话术 / 钩子 / 收尾）→ 分步收藏 / 复制 → 落库 |
| 上下文 | 跟随 Tab 自动识别品牌 / 平台 / 店铺，支持手动切换，支持页面用 URL 参数声明上下文 |
| 检索 | 三级知识库（店铺 > 品牌 > 通用）+ 自实现中文 BM25 与 pgvector 混合打分 + 品牌隔离 |
| 生成 | 单 Agent 直接生成 + 三层结构化输出保障 + DeepSeek → Qwen → 混元降级链 |
| 展示 | 推荐话术置顶常驻，其余四步默认收起，「溯源」按需展开（RAG Top-3） |
| 工程 | 一键安装 / 启动脚本、Docker Compose、Mock / 真实 API 切换、52 项自动化测试 |

### 已知短板（迭代二的输入）

1. **改一步要重算全部**：客服手改第 3 步话术后重新生成，会把已经确认的 1、2 步也改掉，前功尽弃；
2. **长对话会退化**：目前直接拼接历史消息，超过 30 轮后容易「Lost in the Middle」；
3. **只吃文字**：客户常发商品截图、订单截图、故障照片、视频、商品链接，现在都只能靠客服转述；
4. **知识盲区看不见**：模型「不知道」的时候没有信号，知识库缺口靠人肉发现；
5. **效果没有度量**：缺少「AI 建议是否真的被采纳、是否提升转化」的闭环数据；
6. **失败 case 没有沉淀**：生成失败只报错，没有进入 Prompt 迭代流程。

## 二、V1.1 — 质量与体验收口

| # | 事项 | 说明 | 验收标准 |
| --- | --- | --- | --- |
| 1 | 级联重生成 | 五步中任一步被修改后加锁，只重算下游步骤，返回完整五步 | 修改第 1 步只重算 2–5 步；响应中带 `lockedSteps`；单测覆盖「锁定 + 合并」 |
| 2 | RAG 缓存复用 | 重生成时复用上一轮检索结果（存于 `messages.metadata`），避免重复向量检索 | 重生成耗时下降 ≥ 30%（本地基准），检索调用次数为 0 |
| 3 | 上下文分层截断 | 近 15 轮原文 + 15–30 轮增量笔记 + 30 轮以上一句总结 | 40 轮对话下生成质量不下降（人工评估 5 条样本），token 消耗平稳 |
| 4 | 失败 case 落库 | 结构化校验失败 / 超时 / 内容违规统一落 `messages.metadata`，后台可查 | 后台能按「失败类型 + 品牌 + 时间」筛选并导出 |
| 5 | 侧边栏体验细节 | 生成中骨架屏、复制后的二次确认、长文本折叠、键盘可达性 | 组件 E2E 新增用例覆盖；键盘可完成全流程 |

## 三、V1.2 — 团队协作与资产化

| # | 事项 | 说明 | 验收标准 |
| --- | --- | --- | --- |
| 1 | 收藏资产化 | 收藏按「品牌 / 场景 / 步骤」打标签，支持检索与复用，可作为话术模板参与检索 | 后台可按标签检索；被复用的收藏能进入 RAG 候选 |
| 2 | 个人评估报告 | 意图准确度、话术修改率、收藏率、首响时长 + 团队均值对比 + 7 天趋势 | 客服端可看自己的报告；数据来自真实使用埋点而非估算 |
| 3 | 修改率埋点 | 记录「AI 原话术」与「客服实际发送话术」的差异度（编辑距离 / 段落级 diff） | 差异度入库，作为 V2.5 偏好信号的原料 |
| 4 | 权限与隔离 | JWT 中携带可访问 `store_ids`，检索与收藏都按店铺过滤 | 跨店铺检索返回空；集成测试覆盖越权场景 |

## 四、V2.0 — Agent 编排（带明确降级门槛）

目标：让模型自己决定「这次要查什么」，而不是前端把上下文一股脑塞进 Prompt。

| 工具 | 职责 | 检索方式 |
| --- | --- | --- |
| `search_product` | 商品参数 / 价格 / 库存 | pgvector 语义 + SKU 精确匹配 |
| `search_policy` | 退货、保修、平台政策 | BM25 + 向量混合 |
| `search_faq` | 品牌 FAQ | 语义检索 |
| `search_script` | 历史优质话术模板 | 语义 + 标签过滤 |
| `search_image` | 以图搜商品（客户发来的商品图匹配 SKU） | CLIP 向量（独立向量空间） |
| `parse_url` | 解析商品链接 | URL 解析 + ERP API |
| `understand_image` | 理解订单截图 / 故障照片 | 多模态 LLM |
| `understand_video` | 视频关键帧 OCR + 音轨 ASR | 关键帧 + ASR 管道 |

**架构不变的部分**：五步 JSON 协议保持不变——它是短期质量管控手段，也是长期数据标注流水线；Agent 换实现，协议不换。

**上线门槛（先评测再切换）**：

1. 用 30 条真实客服消息做单 Agent vs 编排版对比评测；
2. Tool 调用准确率 ≥ 80% 才允许切换，低于门槛直接保留 V1 的单 Agent 方案（参考 ASA 论文：LLM 在 >80% 情况下知道该调工具却不触发）；
3. 延迟不能高于单 Agent 方案的 1.5 倍（客服侧首响有考核）。

**为什么不用 ReAct**：客服场景的核心是「在正确知识上生成正确话术」，不是多步推理；Think-Act-Observe 循环延迟高，且大多数会话不需要多轮工具交互。

## 五、V2.1 — 多模态输入

四种输入统一路由到结构化上下文，再进入五步生成：

| 输入 | 处理管线 |
| --- | --- |
| 文字 | 直连生成链路（现状） |
| 图片 | 双路并行：CLIP 匹配 SKU（精确识别商品）+ 多模态 LLM 理解场景（订单截图、故障照片） |
| 视频 | 关键帧提取 → 帧图像 OCR + 音轨 ASR → 转文字 → 标准五步流程 |
| 链接 | 解析平台域名 + 商品 ID → 调用 ERP API 查商品信息 → 注入上下文 |

**技术要点**：文字向量（1024 维）与图片向量（768 维，Jina CLIP v2）分表存储、各自建 HNSW 索引，不混合检索。

**验收标准**：以图搜商品 Top-1 命中率 ≥ 70%（自建 30 张商品图测试集）；订单截图理解后生成的回复中，订单号 / 商品名 / 金额字段准确率 100%（宁可不填也不编）。

## 六、V2.5 — 数据飞轮

| # | 事项 | 说明 | 验收标准 |
| --- | --- | --- | --- |
| 1 | 偏好信号挖掘 | 「AI 生成版 vs 人工发送版」差异 + 收藏行为 → 初筛数据集 | 导出可用于 DPO 的样本集（含 prompt / chosen / rejected） |
| 2 | 知识缺失自发现 | RAG Top-1 < 0.7 且模型自判 `knowledge_sufficient=false` 双触发 → 同义 query 语义聚类 → 同一 cluster ≥ 5 次推送后台审核 | 后台能收到「高频未命中问题」列表并一键补录知识 |
| 3 | 店铺趋势感知 | 突增检测（今日 > 7 日均值 × 2）、持续高位（本周 > 4 周均值 × 1.5） | 触发后推送给店铺负责人；误报率可控（连续 2 天确认） |
| 4 | 一键采纳率看板 | 生成 → 复制 → 收藏 → 实际发送 的漏斗 | 按品牌 / 店铺 / 客服维度可查 |

## 七、V3.0 — 效果闭环与专属模型

- **订单数据打通**：售前咨询下单率、客服响应时长与转化的相关性分析（需要 ERP / 平台数据授权）；
- **专属客服模型**：用积累的偏好数据做轻量微调（LoRA/DPO），把品牌口径内化到模型里，降低对长 Prompt 的依赖；
- **多租户与配额**：代运营公司下多团队隔离、模型用量配额与成本看板；
- **稳定性**：生成链路 SLO（P95 < 8s、可用性 99.5%）、灰度发布与回滚方案。

## 九、风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 模型生成错误政策（幻觉） | 直接业务事故 | 只允许基于召回知识作答；知识里没有的字段宁可不填；人工审核前置；失败 case 落库 |
| 多模态成本不可控 | 单次生成成本上升 | 图片先走 CLIP 精确匹配，只有匹配失败才走多模态 LLM；对图片/视频设大小与时长上限 |
| Agent 工具调用不稳定 | 延迟与成本上升 | 设 80% 准确率门槛与延迟上限，不达标自动退回单 Agent |
| 知识库维护成本高 | 覆盖不全，召回质量差 | 通用层复用、品牌层隔离、店铺层只存差异；知识缺失自发现把缺口变成待办 |
| 客服不信任 AI | 采纳率低 | 不自动发送；溯源可查；收藏与修改都能被看见，形成正反馈 |
