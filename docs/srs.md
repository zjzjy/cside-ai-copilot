## 1. 项目概述与产品定位

### 1.1 产品定位

**电商代运营专属客服智能提效引擎**。面向代运营公司的一线客服人员，提供 AI 辅助话术生成、知识检索、服务质量评估能力。

**产品形态：** 后端服务持续运行 + 浏览器扩展以侧边栏形式呈现为主要操作界面。客服在电商平台后台工作时，侧边栏常驻浏览器侧边，无需切屏即可完成全部操作。

### 1.2 核心理念

- **把不可复制的个人经验，变成可共享的团队能力**：资深客服的话术、策略、判断力——通过五步协议结构化沉淀，新人可直接复用
- **赋能而非替代**：AI 作为"带教学的副驾驶"——既帮客服生成话术，也教客服背后的策略逻辑。最终决策权和发送权在客服手中
- **跨平台一致性**：无论客服在淘宝、京东还是拼多多后台操作，同一套话术体系、同一种操作习惯、同一个知识库

### 1.3 三大核心痛点

电商客服行业有三个结构性矛盾，且相互叠加。我们的产品选择聚焦这三个而非泛泛覆盖——因为只有这三个是我们的产品形态（外部工具、浏览器扩展、人机协同）能最直接解决的。

#### 🥇 痛点一：质量鸿沟

> "同一个店铺，资深客服转化率 20%，新人转化率 5%。不是新人不想做好，是他们根本不知道该怎么说。"

| 维度                 | 说明                                                                                                                                                    |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 现象                 | 客服能力参差不齐，同一问题不同客服回答水平天差地别。传统机器人应答生硬、答非所问，伪智能客服投诉同比增长 56%                                            |
| 根因                 | 优质话术存在于资深客服的脑子里，无法复制。新人的成长靠"师傅带徒弟"，周期长、成效不确定                                                                  |
| **我们的解法** | 五步生成法将金牌客服的思维过程产品化（意图→策略→话术→引导→收尾），RAG 知识增强让每句话术都有商品信息/政策条款做事实依据，团队共享话术库沉淀集体智慧 |

#### 🥈 痛点二：效率瓶颈

> "大促期间客服同时接待 20 个客户，打字打到手抽筋，客户排队等到发火。"

| 维度                 | 说明                                                                                                                         |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 现象                 | 首响超 60 秒客户流失 47%，大促期间咨询量暴涨 5-10 倍，客服队伍临时扩充导致服务质量断崖式下跌                                 |
| 根因                 | 客服的核心工作流中，"想怎么回复"占用了大量时间——查商品信息、翻政策条款、斟酌措辞。这些时间无法被压缩，因为回复质量不能牺牲 |
| **我们的解法** | 五步生成法+RAG知识增强（多路召回含FAQ语义检索）统一处理所有提问。客服一键复制发送，决策权保留在人手里                        |

#### 🥉 痛点三：经验流失

> "铁打的产品，流水的客服，永远在培训。"

| 维度                 | 说明                                                                                                                                                                                                            |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 现象                 | 电商客服行业年流失率高达 25%-40%。一个资深客服离职，他积累的几千条优质话术、几百个客户案例、对每款产品的隐性理解——全部带走。新人来了又从零开始                                                                |
| 根因                 | 客服行业普遍缺乏"知识沉淀"机制。对话记录躺在聊天日志里，没有人整理、没有人标注、没有人复用。每次人员流动都是一次知识资产的蒸发                                                                                  |
| **我们的解法** | 五步数据协议将每一条对话结构化存储（客户消息→意图→知识→生成话术→客服修改→实际发送），话术库一键收藏+标签分类+团队共享。**客服会离职，但知识不会**。客服收藏的话术直接进入微调初筛数据集（详见§9.6） |

### 1.4 暗线：话术收藏 → 微调数据飞轮

三个痛点之上，有一条贯穿始终的暗线——**客服的每一次收藏，都在为未来的专属模型积累训练数据**。

```
明线：质量鸿沟 ──→ 效率瓶颈 ──→ 经验流失
        │              │              │
        ▼              ▼              ▼
   五步生成法     多路召回RAG     话术库共享
   +RAG 知识      +知识增强        +数据协议
        │              │              │
        └──────────────┼──────────────┘
                       │
                       ▼
        ┌─────────────────────────────┐
        │        暗线：数据飞轮         │
        │                             │
        │  客服收藏话术 = 微调初筛      │
        │  话术库 = 初筛数据集           │
        │                             │
        │  后续可人工精筛，但无论        │
        │  后续流程如何，收藏即初筛      │
        │                             │
        │  V1.0  Prompt驱动通用LLM     │
        │       + RAG知识增强           │
        │  V1.5  数据积累 → 微调探索    │
        │  V2.0  专属电商客服模型        │
        │        → 但它仍是辅助工具    │
        │                             │
        └─────────────────────────────┘
```

**数据飞轮的核心逻辑（v2.2 修订）：**

飞轮的核心是一个简单规则：**客服收藏的话术库，直接视为后续微调数据集的初筛结果。** 不再对数据进行多层级分类（如L0-L4），不区分修改幅度、修改者身份等维度来判定数据价值。后续可能引入人工精筛环节，但那是后置流程——无论后续如何，收藏库就是初筛。

```
V1.0 冷启动期（当下）
  ├─ 种子数据来源：历史话术导入 + 首批资深客服刻意录入
  ├─ 日常积累：客服使用中收藏的话术 → 自动进入初筛数据集
  ├─ 目标：跑通链路，积累第一批经过验证的结构化对话数据
  └─ 关键动作：首批合作的资深客服每周固定产出 5-10 条话术

V1.5 积累期（数据量达标后）
  ├─ 初筛数据集持续增长（所有客服收藏的话术自动汇入）
  ├─ 可引入人工精筛环节，对初筛数据集做质量把关
  └─ 目标：积累足够的高质量数据，启动第一轮微调实验

V2.0 飞轮期（模型微调验证后）
  ├─ 微调后的模型产出更高质量草稿 → 客服收藏率提升 → 初筛数据集加速增长
  ├─ 收藏即初筛的机制持续运转，形成正反馈循环
  └─ 专属电商客服模型迭代 → 但它始终是辅助工具，决策权和发送权在人手里
```

**设计原则：** 简单胜于复杂。不设多层级数据价值判定标准（修改幅度、修改者身份等），不以"AI 写了多少、人改了多少"来划分数据等级。**收藏 = 初筛**，这一条规则足够清晰且可落地。后续如需人工精筛，是对初筛数据集的二次过滤，不影响"收藏即初筛"的基础机制。

**护城河落点：** 竞品可以抄我们的界面，可以买同一个大模型，但抄不走我们沉淀下来的垂直场景训练数据。**真正值钱的不是模型，是资深客服在日常使用中持续收藏沉淀的高质量结构化对话数据。**

### 1.5 为什么不是"成本黑洞"和"增长瓶颈"

| 痛点                   | 不选为主攻的原因                                                                                                                                                                                                  |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 成本黑洞（人力成本高） | 核心解法是"用自动化替代人力"，但我们没有电商平台 API 接入能力，做不到自动回复。我们的定位是**提升人效**而非**减少编制**——如果面试被追问"降了多少成本"，我们很难给出类似"AI 替代 80% 咨询"这样的数字 |
| 增长瓶颈（被动不转化） | 这个痛点的重要度够高（主动引导可提升转化 15-30%），但它本质上被**质量鸿沟**覆盖——话术质量上去了、自带钩子引导环节了，转化自然提升。单独列为一个痛点反而稀释了前三个焦点的叙事力度                         |

│  │  · 对话工作台（主操作界面）                │    │
│  │  · 话术库管理                             │    │
│  │  · 知识库管理（管理后台为独立Web页面）      │    │

**侧边栏是主要操作界面：** 客服在电商平台后台（淘宝/京东/拼多多等）工作时，侧边栏常驻浏览器右侧。客服选中客户消息文本后，通过快捷键或点击侧边栏按钮触发 AI 生成，结果直接展示在侧边栏中，无需切换到其他页面或应用。管理后台（知识库管理、用户管理等）以独立 Web 页面形式提供，供管理员使用。

### 2.2 运行环境

| 维度                   | 要求                                           |
| ---------------------- | ---------------------------------------------- |
| **客服端浏览器** | Chrome 90+ / Edge 90+（需支持 Side Panel API） |
| **操作系统**     | Windows 10/11 + macOS 双平台支持               |
| **侧边栏**       | PC 端浏览器侧边栏，常驻右侧，宽度可调          |
| **管理后台**     | PC 端 Web 页面，响应式适配                     |
| **后端部署**     | 云服务器（单体应用 + 容器化部署）              |

### 2.3 为什么是侧边栏

| 决策                     | 理由                                                                       |
| ------------------------ | -------------------------------------------------------------------------- |
| 选侧边栏而非独立Web页面  | 客服工作时浏览器一直开着电商后台，侧边栏常驻右侧无需切屏，操作路径最短     |
| 选侧边栏而非弹窗/面板    | 侧边栏常驻不遮挡主内容区，客服可同时看到对话和商品信息；宽度可调，空间充裕 |
| 选浏览器扩展而非桌面应用 | 无需安装独立程序，浏览器内闭环；利用浏览器原生 Side Panel API，稳定性好    |
| 后端独立运行             | LLM调用、RAG检索等计算密集任务在后端完成，侧边栏专注交互展示               |

## 3. 用户角色与权限体系

### 3.1 角色定义

| 角色                 | 权限范围                                                 | 说明                 |
| -------------------- | -------------------------------------------------------- | -------------------- |
| **普通客服**   | 对话工作台、个人话术库、个人数据                         | 核心使用者，日常操作 |
| **系统管理员** | 用户管理、角色管理、平台规则配置、系统设置、全部数据查看 | 系统管理者，全局视角 |

### 3.2 话术库权限

- **个人私有**：客服自己收藏的话术，仅自己可见
- **团队共享**：资深客服的优秀话术可一键分享到团队库，全组成员可见和使用
- **话术库定位**：既是"个人弹药库"，也是"团队知识资产"

## 4. 核心交互流程

### 4.1 选型决策链路

| 问题         | 候选方案                           | 最终选择      | 核心理由                                               |
| ------------ | ---------------------------------- | ------------- | ------------------------------------------------------ |
| 消息获取方式 | A:手动选中文本 / B:平台API自动获取 | **A**   | 不依赖电商平台API，客服选中客户消息文本即可触发        |
| 工具形态边界 | A:侧边栏常驻 / B:独立窗口 / C:弹窗 | **A**   | 侧边栏常驻右侧不遮挡工作区，客服可同时看对话和商品信息 |
| 交互方式     | A:快捷键触发 / B:点击按钮触发      | **A+B** | 快捷键为主（高效），按钮为辅助（可发现性）             |

### 4.2 端到端操作流程

```
┌─────────────────────────────────────────────────────────────┐
│         客服日常操作流程（浏览器侧边栏，多轮对话）               │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  【第 N 轮】客服在电商平台后台看到客户消息                       │
│       │                                                     │
│       ▼                                                     │
│  ① 在电商平台页面中选中客户消息文本 → 按快捷键（Ctrl+Shift+F）    │
│     或点击侧边栏"生成"按钮                                     │
│     （系统自动匹配到当前对话，或客服手动选择/新建对话）            │
│       │                                                     │
│       ▼                                                     │
│  ② 系统根据当前浏览器页面 URL 自动识别**平台+店铺**                  │
│     （如 taobao.com + 店铺标识 → vivo旗舰店-淘宝），                    │
│     据此加载对应品牌的话术风格、平台退货政策、店铺促销活动                │
│       │                                                     │
│       ▼                                                     │
│  ③ 侧边栏自动切换到该店铺的最近活跃对话（如该店铺无对话则新建），         │
│     触发 AI 五步生成（Step1~Step5），                                   │
│     多路召回（含FAQ语义检索）增强知识上下文                               │
│       │                                                     │
│       ▼                                                     │
│  ④ 侧边栏展示五步结果面板：                                    │
│     · 可【重生成】全部五步                                     │
│     · 可【修改任一步】→ 点"应用修改"→ 下游步骤自动级联重生成     │
│     · 可【分步收藏】任一步（⭐）到个人话术库                     │
│     · 可一键复制推荐话术（Step3）                              │
│       │                                                     │
│       ▼                                                     │
│  ⑤ 客服在电商平台后台的聊天输入框中粘贴（Ctrl+V）发送给客户       │
│       │                                                     │
│       ▼                                                     │
│  【第 N+1 轮】客户再次回复                                     │
│       │                                                     │
│       ▼                                                     │
│  ⑥ 客服选中新消息文本 → 再次触发生成                           │
│     → 系统自动携带前N轮上下文 → 循环③~⑤                        │
│       │                                                     │
│       ▼                                                     │
│  ⑦ 对话结束：客服点击"新建对话"或30分钟无活动自动过期            │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**关键交互细节：**

- **侧边栏常驻**：客服在电商平台工作时，侧边栏始终在浏览器右侧打开，无需切屏。侧边栏宽度可拖拽调整。
- **消息获取**：客服在电商平台页面中选中客户消息文本，按快捷键 Ctrl+Shift+F 或点击侧边栏按钮触发生成。选中的文本自动填入侧边栏的当前对话上下文。
- **平台+店铺自动识别**：系统根据当前浏览器页面的 URL 自动识别电商平台和店铺（如 `taobao.com` + 店铺标识 → vivo旗舰店-淘宝），加载对应品牌话术风格、平台退货政策、店铺促销活动。CS 无需手动选择。
- **多店铺上下文自动切换**：代运营客服在千牛/京麦/抖店等后台中切换店铺 Tab 时，页面 URL 随之变化。侧边栏监听 URL 变化，**自动切换**到该店铺的最近活跃对话——加载该店铺的历史消息、该品牌的话术风格、该店铺的促销政策。CS 无需在侧边栏里再手动切一次。
- **手动切换店铺**：侧边栏顶部提供店铺切换下拉菜单，CS 可手动选择当前服务的店铺和平台。适用于 URL 无法自动识别店铺的极端情况。
- **同一个对话ID**：每个对话同时绑定 `store_id`（店铺标识），同一店铺内的消息归入同一对话。不同店铺的对话天然隔离——vivo旗舰店的对话历史不会混入OPPO旗舰店的上下文中。
- **历史消息可见**：侧边栏内展示当前对话的历史消息（客户消息+客服已发送话术），客服随时可回顾上下文。
- **消息字数限制**：输入框最大支持 500 字符，右下角实时显示当前字符数（如 `128/500`），超出时截断并提示。
- **多轮上下文自动拼接**：每次触发五步生成时，系统自动将前N轮对话记录（客户消息+客服实际发送的话术）拼接进LLM上下文。
- **修改级联规则**：改Step1→全部重生成；改Step2→重生成Step2/3/4/5；改Step3→重生成Step3/4/5；改Step4→重生成Step4/5；改Step5→只重生成Step5。上游步骤不受影响。修改后的步骤显示绿色边框（已锁定），下游步骤灰色骨架屏（重新生成中），客服点"应用修改"后才触发级联——避免"还在改但后面自己变了"的失控感。
- **分步收藏**：每个步骤旁边有独立⭐按钮。收藏时自动打标签（当前品牌+平台+意图类别+场景）。Step1收藏→用于验证意图分类评测集；Step2收藏→沉淀为策略模式库；Step3收藏→加入话术模板库（高频者作为多路召回中FAQ检索的优质候选项）；Step4收藏→加入钩子引导模板库；Step5收藏→加入收尾话术模板库。

### 4.3 多轮对话会话管理设计

> **⚠️ 技术调研节点：此为多方案并行调研项，不可直接选定方案进入开发。**

#### 4.3.1 要解决的问题

侧边栏的核心交互是"选中客户消息→触发"——单次触发只接收当前选中的文本。但真实客服对话是多轮的——客户分多次发送消息，上下文分布在多条消息中。系统需要知道"这一条消息属于哪一个对话"，才能将前N轮对话历史拼接进LLM上下文。

典型场景：

```
客户第1轮: "耳机左边不响了"
  → 客服选中文本→触发生成，生成话术A（关于故障排查），发送
客户第2轮: "用了三个月"
  → 客服选中文本→在同一对话中再次触发
  → 系统自动拼接第1轮上下文 → 正确识别为保修判定
客户第3轮: "那能换吗？"
  → 必须关联前两轮才能知道是"用了三个月的耳机左边不响，想换新"
```

#### 4.3.1.1 侧边栏会话UI概念

```
┌─────────────────────────────────────────┐
│  浏览器侧边栏                             │
│                                         │
│  当前对话: [淘宝] vivo TWS 3 售后咨询     │
│  对话ID: #conv_20260715_003  [新建对话]  │
│  ────────────────────────────────────── │
│  历史消息（可折叠）                       │
│  ┌─────────────────────────────────────┐│
│  │ [客户 14:28] 耳机左边不响了，用...    ││
│  │ [客服 14:32] 亲，非常抱歉给您...      ││
│  │ [客户 14:35] 那能换吗？              ││
│  └─────────────────────────────────────┘│
│  ────────────────────────────────────── │
│  当前选中: 那能换吗？                      │
│  [生成] [清空对话]                       │
│  ────────────────────────────────────── │
│  ▼ 五步生成结果展示区                     │
└─────────────────────────────────────────┘
```

**会话生命周期：**

- 客服选中消息触发 → 系统自动创建对话ID（如未指定）
- 同一对话ID内的每一次生成都自动携带前N轮上下文
- 客服可手动"新建对话"切换会话
- 15分钟无活动 → 对话自动过期归档

**上下文拼接规则（传给LLM）：**

| 轮次  | 系统拼接内容                                                                |
| ----- | --------------------------------------------------------------------------- |
| 第1轮 | 客户消息 + 商品上下文（URL/平台）                                           |
| 第2轮 | 客户消息 + 历史{第1轮客户消息, 第1轮AI话术, 第1轮客服实际发送} + 商品上下文 |
| 第N轮 | 客户消息 + 历史{前N-1轮的客户消息+客服实际发送} + 商品上下文                |

**上下文截断策略（需调研）：**

- 方案A：保留最近N轮（如最近5轮），超出部分丢弃
- 方案B：对超出N轮的部分做LLM摘要压缩后拼接
- 方案C：不做截断，超出LLM上下文窗口时由模型自动截断

#### 4.3.2 会话识别候选方案矩阵（并行调研）

| 方案                                 | 核心思路                                                                                                   | 优点                             | 缺点                                                                                   |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------- | -------------------------------- | -------------------------------------------------------------------------------------- |
| **A: 页面DOM全量采集**         | Content Script 持续监听聊天面板DOM，自动采集当前会话窗口内的所有消息气泡，按时间戳排序拼接为上下文         | 客服无需额外操作，上下文自动完整 | 各平台聊天面板DOM结构不同，需要针对性适配；长对话可能超出LLM上下文窗口                 |
| **B: 客服手动标记会话范围**    | 首次触发时弹出"开始会话"，后续每次触发自动归入同一会话；客服可随时"结束会话"或手动切换                     | 实现简单，客服可控性强           | 增加操作步骤，客服可能忘记标记；依赖人的主动性                                         |
| **C: 页面URL/POST参数会话ID**  | 利用电商后台URL中的会话ID参数（如`ticketId`、`sessionId`），扩展从URL中解析，后端据此维护对话历史      | 对客服零侵入，依赖客观标识       | 不同平台URL模式不同；部分平台会话ID可能藏在POST body中不可见                           |
| **D: 剪贴板多轮累积**          | 客服每次触发时，后端自动将当前消息追加到该客服的临时会话缓冲区（如Redis，TTL=30min），前N轮消息一起送入LLM | 不依赖DOM、不依赖URL、实现最通用 | 无法区分"同一个客户的同一段对话"和"不同客户的混入消息"；需要客服手动清理或超时自动过期 |
| **E: 智能消息分组（LLM判断）** | 将最近N条触发记录送给轻模型做两两相似度/关联度判断，自动分组为不同对话                                     | 理论上最智能、最自动化           | 依赖LLM质量，误判代价高；引入额外延迟和成本                                            |

#### 4.3.3 需要调研对比的节点

| 对比项                    | 评测维度                                                                 | 评测数据                                                                 |
| ------------------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------ |
| 方案A vs B vs C vs D vs E | 上下文完整率（是否漏掉关键消息）、客服操作步数、跨平台通用性、实现复杂度 | 模拟5段真实多轮客服对话（每段3-6轮），在各平台（淘宝/京东）DOM环境下验证 |
| 上下文窗口截断策略        | 当对话历史超出LLM上下文限制时，保留最近N轮 vs 摘要压缩 vs 智能裁剪       | 同上数据集，对比不同截断策略下的话术质量变化                             |
| 会话超时策略              | 固定TTL（15min/30min/60min）vs 客服手动结束 vs 自动检测页面关闭          | 模拟客服真实工作中的间隔模式                                             |

#### 4.3.4 对后续的影响

- 会话管理方案的选择直接影响**浏览器扩展 Content Script 的实现复杂度**（方案A/C需要大量DOM适配，方案B/D通用但依赖人工）
- 上下文拼接方式影响**LLM Prompt 的模板设计**——是否需要在Prompt中标注"第1轮/第2轮"来帮助模型理解时序
- 会话存储介质选型影响**Redis的缓存策略**和**数据库的表结构**（是否需要对话历史表）
- 方案选择建议在**P0初期**与CLIP/OCR选型并行完成，避免后期因会话管理不成熟导致整个交互链路返工

## 5. 浏览器扩展（侧边栏）

### 5.1 定位说明

浏览器扩展以**侧边栏（Side Panel）**形式呈现，是本产品的**主要操作界面**。客服在电商平台后台工作时，侧边栏常驻浏览器右侧，无需切屏即可完成话术生成、话术库管理等全部操作。

### 5.2 侧边栏提供的能力

| 能力         | 说明                                                                                             |
| ------------ | ------------------------------------------------------------------------------------------------ |
| 快捷键触发   | 客服在电商平台页面选中客户消息文本后，按 Ctrl+Shift+F 触发生成，选中的文本自动进入当前对话上下文 |
| 侧边栏常驻   | 使用 Chrome Side Panel API，侧边栏常驻浏览器右侧，不遮挡主内容区，宽度可拖拽调整                 |
| 平台自动识别 | 根据当前页面域名自动识别电商平台，加载对应的平台规则和话术风格偏好                               |
| 对话工作台   | 多轮对话管理、历史消息展示、五步结果查看、分步收藏、一键复制话术                                 |
| 话术库管理   | 个人话术库浏览、检索、分类管理                                                                   |
| 通知提醒     | AI 处理完成后侧边栏内高亮提示                                                                    |

### 5.3 侧边栏的技术实现

使用 Chrome Side Panel API（Manifest V3），通过 `chrome.sidePanel.open()` 打开侧边栏。侧边栏内容为独立 HTML 页面，通过后端 API 获取数据。

核心 API：

- `chrome.sidePanel.setPanelBehavior({ openPanelOnActionClick: true })` — 点击扩展图标打开侧边栏
- `chrome.sidePanel.open()` — 程序化打开侧边栏
- `chrome.tabs.sendMessage()` — 与 Content Script 通信获取页面上下文

**多店铺上下文自动切换机制：** Content Script 监听当前页面 URL 变化（代运营客服在千牛/京麦中切换店铺 Tab 时，URL 中的店铺标识会变化）。检测到店铺切换时，通知侧边栏切换到对应店铺的最近活跃对话，自动加载该品牌的话术风格和该店铺的促销政策。CS 无需在侧边栏中手动选择店铺。

### 5.4 面临的已知风险

| 风险类型            | 说明                                                                     | 影响程度 | 应对策略                                                              |
| ------------------- | ------------------------------------------------------------------------ | -------- | --------------------------------------------------------------------- |
| DOM 变化            | 电商平台灰度测试或 A/B 测试可能导致页面 DOM 结构变化，选中文本提取不稳定 | 中       | Side Panel 本身不受 DOM 影响；文本选中基于用户主动选择，降低 DOM 依赖 |
| 平台风控策略        | 电商平台可能检测浏览器扩展行为并采取限制措施                             | 高       | Side Panel 是浏览器原生 API，不会被平台检测为 DOM 注入                |
| Shadow DOM 穿透问题 | 部分平台使用 Shadow DOM 封装界面，可能影响文本选中                       | 中       | 用户手动选中文本，不走 DOM 自动采集，影响有限                         |
| 扩展审核延迟        | Chrome Web Store 审核周期 3-5 天，紧急修复无法快速上线                   | 中       | 后端逻辑独立于扩展，紧急修复可通过后端热更新完成                      |
| Side Panel API 兼容 | Firefox 等浏览器不支持 Chrome Side Panel API                             | 低       | V1.0 仅支持 Chrome/Edge；后续版本考虑 Firefox sidebar_action          |

## 6. 多平台支持策略

### 6.1 选型决策

| 候选方案                              | 描述                                               | 选择 |
| ------------------------------------- | -------------------------------------------------- | ---- |
| A: 全平台统一策略                     | 不区分平台和品牌，完全依赖 AI 通识                 | ❌   |
| B: 按平台硬编码适配                   | 3-4 个平台硬编码策略                               | ❌   |
| **C: 品牌+平台+店铺三级可配置** | 管理后台逐级配置，店铺继承品牌和平台默认值，可覆盖 | ✅   |

### 6.2 三级规则配置模块（管理后台）

代运营客服同时服务多个品牌、多个平台的多家店铺，业务规则的差异来自三个层级。配置采用**继承+覆盖**模式：店铺默认继承品牌和平台的规则，仅需配置差异项。

```
品牌级配置（最高优先级，定义品牌调性）
  ├─ 话术风格（vivo: 专业科技感 / OPPO: 年轻时尚感 / 小米: 性价比亲民）
  ├─ 品牌禁用语（如某品牌不允许承诺"永远不降价"）
  ├─ 品牌专属政策（如 vivo 官旗额外赠送延保服务）
  └─ 品牌默认话术模板（按品类：手机/耳机/平板的卖点话术）

平台级配置
  ├─ 平台退货政策差异（京东自营 vs 淘宝 vs 拼多多）
  ├─ 平台话术风格偏好（抖音偏口语化、京东偏正式）
  └─ 平台特有钩子模板（抖音：引导关注直播间；淘宝：引导领券）

店铺级配置（仅存差异项，覆盖上面两级）
  ├─ 该店特有促销活动（618/双11/店庆等）
  ├─ 该店临时规则调整
  └─ 该店独立的钩子/收尾偏好（如有）
```

**继承逻辑：** 触发话术生成时，系统根据识别到的品牌+平台+店铺，按"店铺 → 品牌 → 平台"的优先级合并配置。店铺有配置的用店铺，没有的继承品牌，品牌没有的继承平台默认值。

**配置项定义：**

| 配置项       | 所属层级 | 说明                   | 示例                                   |
| ------------ | -------- | ---------------------- | -------------------------------------- |
| 品牌话术风格 | 品牌     | 该品牌的语气和调性     | vivo：专业、科技感；OPPO：年轻、时尚   |
| 品牌禁用语   | 品牌     | 该品牌不允许出现的表述 | "永不降价""绝对最低价"等               |
| 品牌专属政策 | 品牌     | 品牌特有的售后规则     | vivo 官旗赠送延保、OPPO 以旧换新补贴   |
| 平台退货政策 | 平台     | 平台特有的退货规则     | 京东自营退货运费政策 vs 淘宝           |
| 平台话术风格 | 平台     | 平台偏好的语气         | 抖音：口语化、有网感；京东：专业、稳重 |
| 平台钩子模板 | 平台     | 平台特有的转化引导     | 抖音：引导关注直播间 vs 淘宝：引导领券 |
| 店铺促销活动 | 店铺     | 该店当前促销           | vivo旗舰店-淘宝：618直降200元          |
| 店铺临时规则 | 店铺     | 该店临时调整           | 该店临时延长退货期限至15天             |

> **核心原则：** 代运营场景下，规则差异来自**品牌、平台、店铺三个维度**。品牌差异（话术调性、禁用语）是最高优先级，平台差异（退货政策）次之，店铺差异（促销活动）是临时覆盖层。平台和店铺通过当前页面 URL 自动识别，无需客服手动选择。

### 6.3 V1.0 覆盖范围

初始配置 1 个品牌（vivo）× 2 个平台（淘宝、京东）× 2-3 家店铺，验证三级继承+覆盖配置架构的可行性。其余品牌和平台后续通过配置扩展。

## 7. 大模型选型与模型中台

### 7.0 技术选型方法论

本项目所有技术选型遵循统一原则：**每个选型决策必须有明确的依据，不能凭感觉或惯性选择。** 选型依据通过以下两种方式获取：

**方式一：实地使用评测（推荐）**

多候选方案在相同的测试数据集上跑评测，用量化指标对比。适用于：LLM模型、Embedding模型、Reranker、OCR方案、CLIP模型等可直接调用API或本地运行的服务。

- 产出：评测对比表（指标矩阵）+ 选型结论 + 权衡说明
- 示例：§7.1 LLM模型选型、§7.2 Agent架构评测、层② Embedding模型选型

**方式二：网络信息调研**

通过查阅官方文档、技术博客、社区讨论、论文、竞品分析等公开资料，综合评估各方案的优劣、生态成熟度、社区活跃度、已知局限性等。适用于：向量数据库选型、部署架构选型、前端框架选型等偏工程基础设施的决策，或无法在短期内搭建评测环境的方案。

- 产出：调研报告（信息来源 + 关键对比维度 + 选型结论 + 权衡说明）
- 要求：至少引用 2 个独立来源；注明信息来源的可信度（官方文档 > 权威技术博客 > 社区讨论）

**无论哪种方式，选型结论必须包含：**

1. **选了谁** — 最终选择的方案
2. **为什么选** — 量化数据或调研依据
3. **放弃了什么** — 候选方案的相对优势及放弃理由

### 7.2 Agent + Tool Router 评测（必须评测，阻塞性调研）

> ⚠️ **调研节点：Agent+Tool Router 是本项目最核心的技术假设之一，但也是风险最高的。** 研究证实 LLM 在工具调用场景下"知道该用工具却不触发调用"的发生率超过 80%（[ASA 论文](https://ar5iv.labs.arxiv.org/html/2602.04935)，工具意图可从中间层激活以 >99% AUC 解码，但模型在超过 80% 的情况下未能触发调用）。**Agent+Tool Router 方案能否在客服场景下可靠工作，必须在 P0 初期通过评测验证，不可跳过。**

示例对比 **单Agent直接生成** vs **Agent + Tool Router（工具编排）**，主要评测指标为话术可用率和Tool调用准确率。评测数据为30条客服消息。

| 架构                | 话术可用率 | Tool调用准确率 | P50延迟 | 单次成本 |
| ------------------- | ---------- | -------------- | ------- | -------- |
| 单Agent直接生成     | ❓         | —             | ❓      | ❓       |
| Agent + Tool Router | ❓         | ❓             | ❓      | ❓       |

**评测结论的决策影响：** 如果 Agent+Tool Router 的 Tool 调用准确率 <80%，则 V1.0 应降级为单 Agent 直接生成方案，待模型能力成熟后再切换。

## 9. 五步生成法 — 产品协议设计

### 9.1 五步定义

| 步骤             | 名称     | 内容                              | 对客服的价值             |
| ---------------- | -------- | --------------------------------- | ------------------------ |
| **Step 1** | 意图识别 | 解析客户诉求、情绪、隐藏需求      | "我理解了客户想要什么"   |
| **Step 2** | 回复策略 | 问题解决 + 情绪安抚的双重逻辑     | "我应该用什么策略回应"   |
| **Step 3** | 推荐话术 | 平台适配、可直接复用的完整脚本    | "我具体说什么"           |
| **Step 4** | 钩子引导 | 挖掘客户利益点，刺激下单/复购决策 | "我怎么促成下一步"       |
| **Step 5** | 成功收尾 | 构建良好体验，铺垫复购转化        | "我怎么让客户满意地结束" |

#### 9.1.1 五步交互能力

客服对五步生成结果拥有完整的编辑和控制权：

| 交互能力                        | 说明                                                   | 触发方式                                                                |
| ------------------------------- | ------------------------------------------------------ | ----------------------------------------------------------------------- |
| **全部重生成**            | 对当前五步结果不满意，丢弃全部重新生成                 | 点击"重新生成"，LLM重新产出完整五步                                     |
| **单步修改 + 级联重生成** | 修改某一步后，下游步骤自动基于新输入重新生成           | 编辑某一步内容 → 点击"应用修改" → 下游步骤灰色骨架屏（生成中）→ 完成 |
| **分步收藏**              | 收藏五步中的任意一步（不限于整条），每步旁边独立⭐按钮 | 点击某步的⭐ → 自动打标签（平台+意图+场景）→ 存入个人话术库对应分类   |

**级联重生成规则：**

```
改Step1（意图）→ Step1/2/3/4/5 全部重生成
改Step2（策略）→ Step2/3/4/5 重生成，Step1不变
改Step3（话术）→ Step3/4/5 重生成，Step1/2不变
改Step4（钩子）→ Step4/5 重生成，Step1/2/3不变
改Step5（收尾）→ 仅Step5重生成
```

**交互约束：**

- 修改后的步骤显示**绿色边框**（已锁定），下游待生成步骤显示**灰色骨架屏**（等待中）
- 客服必须点击"应用修改"后才触发级联——避免"还在编辑但后面的自己变了"的失控感
- 级联重生成是一次额外的LLM调用，入参为：被修改的步内容 + 客户原始消息 + 已检索知识 + 上游未变步骤

**分步收藏的数据去向：**

| 收藏的步骤        | 存入分类         | 后续用途                                                  |
| ----------------- | ---------------- | --------------------------------------------------------- |
| Step1（意图识别） | "意图案例"       | 验证和补充意图分类评测集                                  |
| Step2（回复策略） | "策略模式库"     | 按场景/意图分类，遇到类似场景直接复用策略逻辑             |
| Step3（推荐话术） | "话术模板库"     | 可直接复用的话术；高频者作为多路召回中FAQ检索的优质候选项 |
| Step4（钩子引导） | "钩子引导模板库" | 按平台/场景分类，跨对话复用                               |
| Step5（成功收尾） | "收尾话术模板库" | 按场景分类复用                                            |
| 整条五步          | "完整话术案例"   | 收藏即进入微调初筛数据集（详见§1.4）                     |

### 9.3 五步法与 Agent 的关系

**五步法 ≠ Agent。它们是"协议"和"引擎"的关系：**

| 维度               | Agent                              | 五步生成法                     |
| ------------------ | ---------------------------------- | ------------------------------ |
| **是什么**   | 推理引擎                           | 输出格式 + 数据协议            |
| **层次**     | 技术层（用户不可见）               | 产品层（用户可见）             |
| **职责**     | "怎么想"——理解、检索、推理、决策 | "怎么呈现"——结构化展示和沉淀 |
| **变化**     | 随技术升级可以换引擎               | 格式保持稳定，保证数据一致性   |
| **长期价值** | 效率工具（当下价值）               | 数据飞轮（未来价值）           |

```
Agent（引擎）            五步生成法（协议）
┌────────────┐          ┌────────────┐
│ 意图理解    │          │ Step 1     │
│ 检索决策    │ ──填充──→ │ Step 2     │
│ 工具编排    │          │ Step 3     │
│ 策略推理    │          │ Step 4     │
│ 质量自评    │          │ Step 5     │
└────────────┘          └────────────┘
     ↓                       ↓
  可以换引擎              格式永远不变
  V1: Prompt Agent      数据持续积累
  V1.5: RAG Agent       模型越来越好
  V2: 微调模型
  V3: 自主Agent
```

### 9.5 结构化输出保障机制

五步生成法的 JSON Schema 定义了理想的数据格式，但 LLM 的实际输出并非总是严格遵循 Schema——尤其在模型降级切换时（层⑥ L1/L2），不同模型的 JSON 输出可靠性差异显著。需要多层保障机制确保结构化输出的完整性和可用性。

#### 9.5.1 三层保障架构

```
第一层：结构化输出约束（主动预防）
  ├─ 调用 LLM 时启用 JSON Mode / Structured Output（如 OpenAI response_format）
  ├─ 如模型不支持原生 JSON Mode，使用 Function Calling 的 tool_choice 强制结构化
  └─ Prompt 中显式声明："请严格按照以下JSON Schema输出，不要添加Schema之外的字段"

第二层：输出格式校验（被动检测）
  ├─ JSON 解析校验：LLM 返回后立即 try-parse，解析失败→重试1次（同模型）
  ├─ Schema 完整性校验：五步是否齐全（step1~step5 全部非空且非null）
  ├─ 内容长度校验：每步 content 不少于最小长度阈值（如 step3_script ≥ 20字）
  ├─ 字段类型校验：如 `rating` 必须是 1-5 整数，`modified` 必须是 boolean
  └─ 校验失败→如为重试，切换到备用模型重新生成；如备用模型也失败→进入第三层

第三层：降级兜底（保证不阻断）
  ├─ 部分缺失：缺失的步骤标灰显示（如 step4 缺失→面板显示"钩子引导：暂未生成"）
  ├─ 完全失败：降级为纯文本模式，不按五步展示，只展示 LLM 原始回复文本
  ├─ 用户提示：每种降级状态均在前端显示明确的状态标记（🟢完整 / 🟠部分缺失 / 🔴降级纯文本）
  └─ 日志记录：所有校验失败的 case 完整记录（原始 LLM 输出 + 校验错误详情），用于后续模型评测和Prompt优化
```

#### 9.5.2 校验规则定义

| 校验项              | 规则                                               | 失败处理                                         | 对应层⑥降级级别 |
| ------------------- | -------------------------------------------------- | ------------------------------------------------ | ---------------- |
| JSON 可解析         | `JSON.parse(raw_output)` 不抛异常                | 同模型重试1次；仍失败→切备用模型重试            | L2 备用模型模式  |
| step1_intent 存在   | 字段非空且长度 ≥ 10字                             | 该步骤标灰，其他步骤正常展示                     | 🟠 部分缺失      |
| step2_strategy 存在 | 字段非空且长度 ≥ 10字                             | 同上                                             | 🟠 部分缺失      |
| step3_script 存在   | 字段非空且长度 ≥ 20字                             | **核心话术缺失→整条作废，切模型重试**     | L1/L2 降级       |
| step4_hook 存在     | 字段非空且长度 ≥ 5字                              | 标灰展示，不影响 step3 使用                      | 🟠 部分缺失      |
| step5_close 存在    | 字段非空且长度 ≥ 5字                              | 标灰展示，不影响 step3 使用                      | 🟠 部分缺失      |
| intent 标签合法     | `intent` 值在预定义分类集合内                    | 保留原输出，前端不显示意图标签（降级为"未分类"） | 🟠 部分缺失      |
| agent_trace 完整性  | `retrieved_knowledge` 和 `tool_calls` 非空数组 | 不影响前端展示，仅标记日志用于排查 RAG 链路问题  | —（仅日志）     |

#### 9.5.3 需要评测的节点

| 评测项                      | 方法                                    | 量化指标                         |
| --------------------------- | --------------------------------------- | -------------------------------- |
| 各模型 JSON Mode 原生支持度 | 各候选模型调用100次，统计JSON解析成功率 | 解析成功率、平均格式偏差类型分布 |
| Schema 完整性               | 同100条输出，五步齐全率                 | 各步缺失率、模型间差异           |
| 重试策略效果                | 模拟首次输出失败→重试的成功率          | 重试命中率、重试后仍失败率       |
| 降级链路端到端              | 强制触发L1/L2降级，验证三层保障全部走通 | 各降级路径的覆盖率               |

#### 9.5.4 对后续的影响

- 校验规则中的阈值（如 step3 最小20字）需要在**层⑤ LLM-Judge 评测**中校准——太短可能漏掉有价值的话术，太长可能因格式问题误杀
- JSON Schema 是向后兼容的——新增字段不影响旧版解析，但**删除/重命名字段**需要同步更新校验规则和前端展示逻辑
- 所有校验失败的原始输出需要落库（建议存到 ES 日志或专门的分析表），这是**Prompt 迭代优化**的核心数据来源——比人工标注更直接地反映了"模型在哪些场景下输出不稳定"

### 9.6 话术收藏与微调数据初筛

#### 9.6.1 核心规则：收藏即初筛

不再对五步协议产生的数据进行多层级价值分类（如按修改幅度、修改者身份划分L0-L4等级别）。数据飞轮的基础机制简化为一条规则：

> **客服收藏的话术，直接视为后续微调数据集的初筛结果。**

- 客服（无论资深或新手）收藏了某条话术 → 该话术自动进入微调初筛数据集
- 初筛数据集是后续人工精筛的输入——人工精筛可能存在，也可能不存在，但无论如何，收藏即初筛
- 不设复杂的"修改幅度判定""修改者身份分级"等中间层——简单、清晰、可落地
- **收藏自动打品牌标签**：收藏时系统根据当前识别的品牌（如 vivo / OPPO / 小米）自动打上品牌标签。品牌标签确保vivo场景下收藏的话术不会被错误用于OPPO场景的微调数据中，保证后续微调数据集按品牌隔离

#### 9.6.2 反馈闭环

系统通过以下路径采集反馈，**不要求客服额外填写评分或表单**：

**路径一：话术收藏（一键操作）**

- 客服收藏五步中的任一步或整条 → 自动进入个人话术库 + 微调初筛数据集
- 分步收藏同样生效（收藏Step3进入初筛的仅是该条话术，而非整条五步）
- 收藏即信号——不需要额外判断"改了多少""谁收藏的"

**路径二：会话评估报告嵌入标注（一次点击，零摩擦）**

每个会话结束后的评估报告中（见 §8.2 P2 "智能评估报告"），末尾嵌入一个问题和一个按钮：

> **"本会话中客服实际发送的话术，是否值得作为团队模板？"**
> `[是，加入团队模板库]` `[否]` `[稍后再说]`

设计要点：

- 不弹窗、不强制、不阻断——就嵌在评估报告底部，客服看完报告顺手点一下
- 标注"是"的话术 → 自动进入微调初筛数据集
- 这一点击本质上是**为后续微调提供人类偏好标签**

**路径三：AI 失败后的从零录入引导（情绪+记忆都在的时刻）**

当一整个会话中 AI 置信度持续 <0.5 且客服未采纳任何 AI 话术时，会话结束的评估报告顶部增加：

> "本次会话 AI 未能提供有效话术。您是否愿意**录入您实际使用的回复**，帮助团队补上这个场景？`[立即录入]`"

这是"从零录入"发生的正确时刻：

- 客服刚经历了一次 AI 失败的会话，**对"该怎么说才对"有最清晰的记忆**
- 情绪驱动——"AI 不行，让我来"——比"没事去话术库写一条"自然得多
- 点击后跳转到一个极简录入框（预填当前会话的平台+意图标签，客服只需写话术正文）
- 录入的话术自动进入微调初筛数据集

#### 9.6.3 分步收藏的用途

客服可收藏五步中的**任意一步**而非只能收藏整条话术。分步收藏的价值在于——客服的真实需求经常是拆开的（"这个策略很好但话术太软"、"这个钩子很自然但意图分析不对"）。

| 收藏的步骤        | 存入分类         | 后续用途                                                  |
| ----------------- | ---------------- | --------------------------------------------------------- |
| Step1（意图识别） | "意图案例"       | 验证和补充意图分类评测集                                  |
| Step2（回复策略） | "策略模式库"     | 按场景/意图分类，遇到类似场景直接复用策略逻辑             |
| Step3（推荐话术） | "话术模板库"     | 可直接复用的话术；高频者作为多路召回中FAQ检索的优质候选项 |
| Step4（钩子引导） | "钩子引导模板库" | 按平台/场景分类，跨对话复用                               |
| Step5（成功收尾） | "收尾话术模板库" | 按场景分类复用                                            |
| 整条五步          | "完整话术案例"   | 全链路参考；收藏即进入微调初筛数据集                      |

**分步收藏与初筛数据集的关系：**

- 分步收藏与整条收藏同等效力——收藏即进入初筛数据集
- 分步收藏的数据粒度更细，更适合**模块化复用**（如把A场景的Step4钩子用到B场景的回复中）
- 后续如需人工精筛，是对初筛数据集的二次过滤，不影响"收藏即初筛"的基础机制

```
层⑥ 工程边界 & 兜底策略
层⑤ 评测体系（贯穿所有层）
层④ Agent 架构（推理-规划-执行）
层③ Chunking 策略（知识如何切分）
层② 检索策略（如何找到正确的知识）
层① 知识源设计（知识是什么、从哪来）
```

### 层① 知识源设计

#### 1.1 知识类型全景

RAG知识库的知识按**"通用→品牌→店铺"三级组织**，配合物理场景分类和虚拟标签实现高效检索。知识由两大来源构成：**话术库**（系统内生产）+ **商品知识库**（商家导入）。

| 知识类型               | 来源                              | 存储方式                      | 检索方式                  | 所属层级                   | 更新频率         |
| ---------------------- | --------------------------------- | ----------------------------- | ------------------------- | -------------------------- | ---------------- |
| **通用话术**     | 系统预置 + 客服共享               | PostgreSQL + 向量索引         | 语义检索                  | 通用层（全矩阵共享）       | 低               |

| **品牌禁用语**   | 管理员配置（§6.2）               | PostgreSQL（规则表）          | 品牌匹配精准加载          | 品牌层（按品牌隔离）       | 低               |
| **品牌FAQ**      | Mock_Data + 客服收藏Step3沉淀     | Q-A 对 + 向量索引             | 语义检索 + 品牌过滤       | 品牌层（按品牌隔离）       | 低               |

| **店铺促销活动** | 商家上传活动说明                  | 文档 + 向量索引               | 混合检索 + 时效过滤       | 店铺层（单店）             | 高（活动期）     |
| **商品图片特征** | 品牌方图片素材                    | CLIP 向量                     | CLIP 余弦相似度           | 品牌层（按品牌隔离）       | 随商品更新       |

#### 1.0 FAQ 的定位：多路召回中的一条路径

FAQ 不再作为五步生成之前的独立过滤环节存在。FAQ 是多路召回中的一个检索通道，与商品检索、政策检索、话术模板检索并行执行，检索结果合并后统一注入 LLM Prompt。

FAQ语料的持续丰富机制：

- 初始库存：Mock_Data已有30对FAQ + 导入商家现有的Excel快捷短语
- 自动发现：系统统计高频query，未覆盖者自动标记"待添加FAQ"
- 客服收藏的Step3话术 → 自动进入FAQ召回候选池
- 管理员定期审核：组长每周15分钟review"待添加FAQ"列表

FAQ召回效果是检索质量指标之一，不单独设拦截率KPI。

#### 1.0.1 知识库组织方式：通用 → 品牌 → 店铺三级结构

针对代运营客服**跨品牌、跨平台、跨店铺**同时服务的场景，知识库采用三级结构：通用知识全矩阵共享（约80%），品牌知识按品牌隔离（约15%），店铺知识仅存差异项（约5%）。物理上按**使用场景**分类组织（树状目录≤4层），逻辑上通过**虚拟标签**标记品牌/平台/店铺归属。

```

├─ 01_开场欢迎                           ├─ 品牌：通用 / vivo / OPPO / 小米

    └─ 双11专区                          └──────────────────────────┘
```

**三级检索的继承+覆盖逻辑：**

```
CS 在 vivo旗舰店-淘宝 触发话术生成:
  ① 系统识别当前上下文 → 品牌=vivo, 平台=淘宝, 店铺=vivo旗舰店-淘宝
  ② 检索执行：
     店铺层检索（vivo旗舰店-淘宝的促销活动）
       ↓ 未命中或结果不足
     品牌层检索（vivo 品牌FAQ + vivo 话术模板 + vivo 商品参数）
       ↓ 未命中或结果不足
     通用层检索（通用物流话术、退款流程、平台公共政策）
  ③ 品牌禁用语过滤：品牌层检索到的话术自动通过vivo禁用语检查
  ④ 合并结果 → 按"店铺 > 品牌 > 通用"优先级排序 → 注入LLM Prompt
  ⑤ Prompt中携带当前上下文标签：品牌=vivo, 话术风格=专业科技感, 平台=淘宝
```

**客服-店铺关联：** 一个客服可同时关联多个品牌的多个店铺。触发话术生成时，系统根据侧边栏自动识别的当前店铺，按上述继承逻辑限定检索范围——**vivo的退货政策绝不会出现在OPPO客户的回复上下文中**。

**场景分类 + 虚拟标签的优势：**

- CS 按使用场景找话术（符合直觉），品牌归属由系统自动过滤
- 新增品牌只需添加品牌层知识+品牌标签，不需要改动通用层
- 店铺促销活动结束后，仅归档店铺层，不影响品牌层和通用层
- 品牌禁用语在检索阶段自动过滤，不依赖 CS 记忆

#### 1.0.2 RAG的定位：嵌入话术推荐环节，补充召回匹配

RAG并非独立的"搜索功能"——它直接嵌入在五步生成流程中，为Step3（推荐话术）提供事实支撑：

```
客户消息
    │
    ▼
意图识别（Step1）
    │
    ▼
回复策略（Step2）
    │
    ▼
┌──── 推荐话术（Step3）← 此处嵌入RAG多路召回 ────┐
│                                                │
│  RAG多路召回（并行执行）：                        │
│  ① 商品知识库 → 精确匹配SKU参数/价格              │
│  ② 政策规则库 → 检索适用条款                      │
│  ③ 话术模板库 → 语义检索相似场景话术              │
│  ④ FAQ语料库 → 语义检索常见问题的标准回答          │
│  → 多路结果合并 → 注入LLM Prompt                  │
│                                                │
└────────────────────────────────────────────────┘
    │
    ▼
钩子引导（Step4）+ 成功收尾（Step5）
```

RAG的核心价值不是"搜索"，而是**补充召回匹配的相关内容**——让LLM在生成话术时，有真实商品数据、有效政策条款、历史优质话术作为事实锚点，减少幻觉、提升准确度。

#### 1.0.3 多模态输入支持（当前+未来）

**未来扩展：**

| 输入类型               | 处理流水线                                                   | 状态     |
| ---------------------- | ------------------------------------------------------------ | -------- |
| 商品图片               | CLIP匹配 → 识别商品 → 补充商品信息到上下文                 | V1.0 P1  |
| 订单截图/聊天记录截图  | OCR → 提取文字 → 合并到消息文本                            | V1.0 P1  |
| 文件（PDF/Word/Excel） | 文档解析 → 提取文字 → 意图识别                             | 后续版本 |
| 视频                   | **视频 → 提取关键帧 → 转文字（ASR/OCR）→ 意图识别** | 后续版本 |
| 语音消息               | ASR语音转文字 → 意图识别                                    | 后续版本 |

**视频多模态的设计思路：** 不直接对视频做语义理解（计算成本过高）。先将视频转为文字——提取关键帧做OCR、提取音轨做ASR语音识别——得到文本后，再进入标准的意图识别和五步生成流程。视频本身的信息通过"关键帧截图"保留，类似图片的处理方式。

#### 1.1.1 知识刷新触发条件

知识库需要在合理时机触发更新，避免"系统在用但知识已过期"的静默退化。以下按知识类型定义刷新触发条件：

| 知识类型                      | 所属层级 | 刷新触发条件                                                                                | 触发方式                                      | 过期判定                                                      | 未刷新风险                                    |
| ----------------------------- | -------- | ------------------------------------------------------------------------------------------- | --------------------------------------------- | ------------------------------------------------------------- | --------------------------------------------- |
| **通用话术**            | 通用层   | ① 管理员审核通过新话术后入库 ② 话术连续90天未被检索命中→标记"低频"                       | 人工触发（审核/共享）                         | 连续90天未被使用→标记"低频"，不自动删除                      | 话术风格老化，但不直接影响正确性              |
| **品牌商品信息**        | 品牌层   | ① 品牌方在管理后台导入新CSV ② 商品上新/下架/改价后手动触发                                | CSV导入触发全量刷新；单商品可通过管理后台编辑 | `updated_at` 超过30天未更新→后台标记 ⚠️                  | AI引用已下架/已变价商品信息，话术成为虚假承诺 |
| **品牌话术风格/禁用语** | 品牌层   | ① 品牌方更新话术规范 ② 管理员手动修改                                                     | 管理后台手动更新                              | 不设自动过期                                                  | 品牌口径不一致，话术串味                      |
| **品牌FAQ**             | 品牌层   | ① 同一query连续3次被客服修改话术→自动标记"FAQ待补充" ② 管理员手动审核后入库              | 系统自动标记 + 人工审核入库                   | 连续30天未被检索命中→降低权重；90天未命中→归档              | FAQ陈旧影响检索效率                           |
| **品牌话术模板**        | 品牌层   | ① 客服收藏话术自动沉淀 ② 管理员审核通过后入库                                             | 系统自动沉淀 + 人工审核                       | 连续90天未被使用→标记"低频"                                  | 话术模板陈旧，影响生成质量                    |
| **平台公共政策**        | 通用层   | ① 平台（淘宝/京东/拼多多）官方规则变更通知 ② 管理员手动更新                               | 手动更新为主（依赖管理员关注平台公告）        | 文档级别：超过90天未更新，后台标记"待确认"                    | 退换货政策不一致，AI给出错误承诺，引发客诉    |
| **店铺政策规则**        | 店铺层   | ① 品牌方/商家上传新版政策文档 ② 覆盖品牌层默认规则时需手动标注                            | 文档替换后触发该文档对应Chunk的批量重新索引   | 同品牌层：超过90天未更新，后台标记"待确认"                    | 店铺特殊规则未生效，覆盖逻辑失效              |
| **店铺促销活动**        | 店铺层   | ① 活动开始/结束时自动切换状态 ② 活动规则变更时商家手动更新                                | 活动时间驱动 + 商家手动触发                   | 活动结束时间到达后自动标记为`expired`，向量索引降权但不删除 | AI推荐已结束的促销活动，客户投诉"虚假宣传"    |
| **商品图片特征**        | 品牌层   | ① 商品库CSV中`image_urls` 字段更新时联动重新生成CLIP向量 ② 商品上新时随商品信息一起入库 | 商品库变更联动触发                            | 图片URL返回404时标记失效（定时巡检，每周一次）                | CLIP匹配失败率上升，以图搜商品命中率下降      |

**设计原则：**

- **时效性敏感的知识**（促销活动、政策规则）需要**自动过期机制**，不能只靠人记
- **核心依赖知识**（商品信息、平台政策差异）需要**联动刷新**——商品变了图也要变，政策变了差异也要变
- **知识缺失 ≠ 知识过期**——"查不到"归类到层⑥的 RAG 无结果兜底，但"查到了但内容是旧的"是这里要解决的问题
- P2的"知识缺失自发现"解决的是**从未入库的知识**，本节的触发条件解决的是**已入库但过期了的知识**——两者互补

**OCR 选型需要调研的方案：**

| 候选方案            | 运行位置 | 量化指标                   |
| ------------------- | -------- | -------------------------- |
| Tesseract.js (Wasm) | 浏览器端 | 字符准确率、延迟、是否离线 |
| PaddleOCR           | 服务端   | ←                         |
| 通义千问 OCR API    | 云端     | ←                         |

**GPU/运行位置策略：** OCR 的三类候选方案代表了三种运行模式——浏览器端（Tesseract.js Wasm，离线但精度/速度有限）、服务端自部署（PaddleOCR，需GPU服务器）、云端 API（通义千问等，按量付费但零运维）。**V1.0 优先选用云端 API**：OCR 触发频率不高（不是所有对话都有图片），按量付费比自建 GPU 服务更经济；同时保留 Tesseract.js 作为浏览器端兜底（网络断开时的离线 OCR，精度虽低但不断链路）。

### 层② 检索策略

#### 2.1 要解决的问题

客户说"耳机左边不响了"，系统要从知识库里找到最相关的商品信息 + 保修政策 + 历史相似案例。

#### 2.2 候选方案矩阵

| 方案                   | 原理                      | 优点               | 缺点                |
| ---------------------- | ------------------------- | ------------------ | ------------------- |
| A: 纯语义检索          | Embedding → 向量相似度   | 理解同义词/近义词  | 精确型号/数字匹配弱 |
| B: BM25 关键词         | 词频-逆文档频率           | 精确匹配强，可解释 | 不理解语义          |
| C: 混合检索 (Hybrid)   | BM25 + 语义向量，加权融合 | 兼顾精准和语义     | 权重需要调优        |
| D: 多路召回 + Reranker | 多路并行 → 统一排序      | 覆盖面最广         | 延迟和成本增加      |

#### 2.3 需要调研对比的节点

**节点 2.1：Embedding 模型选型**

| 候选模型               | 评测数据                       | 量化指标            | 对后续影响                  |
| ---------------------- | ------------------------------ | ------------------- | --------------------------- |
| text2vec-large-chinese | 50对query-doc，标注相关/不相关 | Recall@5, MRR, NDCG | 影响所有 RAG 查询的召回基线 |
| BGE-large-zh-v1.5      | ←                             | ←                  | ←                          |
| m3e-base               | ←                             | ←                  | ←                          |
| 豆包 Embedding API     | ←                             | ←                  | ←                          |
| 千问 Embedding API     | ←                             | ←                  | ←                          |

**验证方式：** 同一测试集跑所有候选模型，记录 Recall@5 矩阵，出排名。结合延迟和成本，出最终推荐。

**GPU/云端策略：** 本地 Embedding 模型（text2vec/BGE/m3e）在 CPU 上推理速度极慢（尤其 m3e-base 以上的大模型），生产环境需要 GPU。V1.0 优先对比两路：**① 云端 Embedding API**（豆包/千问 Embedding API，零运维、按量付费、延迟稳定）vs **② 本地轻量 Embedding 模型**（如 text2vec-small 在 CPU 上勉强可用，但 Recall 可能达不到85% 达标线）。评测时需同时记录各方案的单次 Embedding 调用成本——如果云端 API 成本低于 GPU 服务器月租，V1.0 无需犹豫。

**节点 2.2：检索架构**

直接选用**混合检索（BM25 + 向量）**，不做纯向量和多路召回的对比实验。BM25保证精确关键词匹配，向量检索保证语义泛化能力，两者互补。

权重设定：α=0.5（等权融合），后续根据实际检索效果微调。

**节点 2.3：向量数据库选型**

直接选用**pgvector**。选择理由：

- 团队PostgreSQL技术栈统一，不引入新数据库
- 部署最简单，复用现有PostgreSQL实例
- 向量索引与业务数据同库，避免跨服务查询
- 无需额外运维成本

**节点 2.4：Reranker 价值验证**

| 方案                | 评测数据        | 量化指标                    |
| ------------------- | --------------- | --------------------------- |
| 不引入 Reranker     | 同50对query-doc | 基线 Recall@5               |
| BGE-Reranker-large  | ←              | Recall@5 提升幅度、额外延迟 |
| 通义千问 Rerank API | ←              | ←                          |
| LLM 做 Rerank       | ←              | ←                          |

**验证方式：** 检索初排取 top-20 → 分别用三种 Reranker 重排 → 对比最终 top-5 的命中率提升和延迟增加。

#### 2.4 层② 对后续的影响

- Embedding 模型直接决定**所有 Chunking 策略的向量维度**
- 检索架构是 Agent 的**核心依赖**——检索质量上限决定了 Agent 话术生成的上限
- 向量数据库选型影响 **Chunking 策略的元数据过滤**能力（如按平台/品类过滤）

### 层③ Chunking 策略

#### 3.1 要解决的问题

一份退货政策文档 5 页长，里面有"七天无理由""质量问题""运费承担"三个独立规则。怎么切才能让查"运费谁出"时精确命中？

#### 3.2 挑战：文档类型不统一

```
品牌商品信息 CSV   →  高度结构化，字段明确，一行一个实体（品牌层）
店铺政策规则文档   →  半结构化，有章节层级，规则之间有交叉引用（店铺层/品牌层继承）
品牌FAQ 语料      →  短文本对（Q-A），天然独立单元（品牌层）
店铺促销活动规则   →  非结构化，自然语言描述，变化频繁（店铺层）
品牌话术模板       →  结构化（五步格式），本身就是分步的（品牌层）
通用话术           →  短文本，按场景分类（通用层，全矩阵共享）
```

#### 3.3 候选方案矩阵

| 方案                | 做法                               | 适合       | 不适合                         |
| ------------------- | ---------------------------------- | ---------- | ------------------------------ |
| A: 统一固定长度     | 所有文档按固定token切，overlap固定 | 简单省事   | 商品CSV被乱切、FAQ的Q和A被分开 |
| B: 按文档类型分策略 | 不同文档用不同切法                 | 适配性好   | 实现复杂，维护成本高           |
| C: 语义切分         | 用模型判断语义边界，自适应切分     | 政策文档   | 对格式有要求                   |
| D: 多粒度索引       | 同一段知识存多个粒度               | 覆盖面最广 | 存储膨胀、检索噪音大           |

#### 3.4 策略落地

直接按§3.5推荐的最终策略实现，不做Chunk大小和分类型策略的对比实验。§3.5的推荐策略已综合考虑文档类型差异和检索效果，V1.0以此为准实现。

#### 3.5 推荐的最终策略（待评测验证）

| 文档类型     | 所属层级 | 切分策略                   | Chunk 大小 | Meta 标签                              |
| ------------ | -------- | -------------------------- | ---------- | -------------------------------------- |
| 通用话术     | 通用层   | 按场景+核心动作切分        | ~256 token | 场景、情绪、时效                       |
| 品牌商品信息 | 品牌层   | 按 SKU 实体（一行一Chunk） | 不固定     | 品牌、品类、平台                       |
| 品牌话术风格 | 品牌层   | 不切分（规则表，精准匹配） | —         | 品牌                                   |
| 品牌FAQ      | 品牌层   | 按 Q-A 对（不可拆分）      | 不固定     | 品牌、问题分类、品类                   |
| 品牌话术模板 | 品牌层   | 按"步"切（每步一个Chunk）  | 不固定     | 品牌、场景、平台、品类                 |
| 平台公共政策 | 通用层   | 语义切分（按章节/条款）    | ~512 token | 政策类型、平台                         |
| 店铺政策规则 | 店铺层   | 语义切分（按章节/条款）    | ~512 token | 店铺、政策类型、平台（继承品牌标签）   |
| 店铺促销活动 | 店铺层   | 语义切分                   | ~512 token | 店铺、活动类型、有效期（继承品牌标签） |

#### 3.6 层③ 对后续的影响

- Chunking 粒度直接决定 Agent 检索后拿到的**上下文完整度**
- 大 Chunk → Agent 上下文更完整但可能噪音多 → 影响话术精准度
- 小 Chunk → 精准但可能缺少关联信息 → Agent 需额外检索补全
- 分类型策略的 Meta 标签需要**在向量数据库建索引时写入**，影响数据导入流程

### 层④ Agent 架构

#### 4.1 要解决的问题

Agent 不只是"调一次 RAG"，而是要**推理 + 规划 + 执行**。理解意图 → 决策检索策略 → 调用工具 → 综合知识 → 生成回复。

#### 4.2 方案选定 — Orchestrator 模式（V2.6 确认）

> **2026-07-26 确认：采用 Orchestrator 模式。** 经过业界方案调研（Synerow、Typewise、Voiceflow、NICE、Bitmovin），确认 CSide 不需要大企业的"状态机+LLM"双轨架构——CSide 工具 ≤8 个、全为只读检索、人工在回路兜底。业界共识：纯 Function Calling 在 ≤10 个工具时表现优秀。

**Orchestrator 模式定义：** 一个总指挥 LLM 收到请求后，自主分析任务 → 决定调哪些工具 + 顺序 → 逐个执行 → 汇总 → 生成五步。

#### 4.3 CSide 工具集（8个）

| 工具 | 触发条件 | 功能 |
|------|---------|------|
| `search_product` | 客户问产品相关问题 | RAG检索商品知识 |
| `search_policy` | 客户问退换/保修/政策 | 检索平台+品牌政策 |
| `search_faq` | 客户问常见问题 | 检索FAQ |
| `search_script` | 客服需要话术参考 | 检索话术模板库 |
| `search_image` | 客户发商品照片 | CLIP以图搜商品 |
| `understand_image` | 客户发截图/故障图 | 多模态LLM理解内容 |
| `resolve_link` | 客户消息含商品链接 | 解析链接→ERP查商品 |
| `understand_video` | 客户发视频 | 多模态LLM理解内容 |

#### 4.4 输入路由

| 输入类型 | 处理方式 | 状态 |
|---------|---------|------|
| 文字 | 意图识别→Orchestrator→RAG→五步生成 | ✅ |
| 图片-以图搜图 | CLIP(Jina CLIP v2) 匹配商品库→注入商品信息 | 🔧 |
| 图片-内容理解 | 多模态LLM直接理解→合并到消息 | 🔧 |
| HTTP链接 | 解析商品ID→ERP API查商品→注入上下文 | 🔧 |
| 视频 | 多模态LLM理解→合并到消息 | 🔧 |
| 语音 | 不做（场景极少） | ❌ |

图片路径由多模态 LLM 一次调用同时判断"类型"和处理"内容"。

#### 4.5 工具失败降级（三级）

```
Level 1: 跳过失败工具 → 用其他可用工具继续 → 告知"XX信息暂时获取不到"
Level 2: 所有检索挂 → 纯LLM兜底 → 标注"⚠️未检索到实时信息，仅供参考"
Level 3: LLM也挂 → 固定话术"暂无法处理，建议联系人工"
```

核心原则: 永远给客服一个响应，宁可降级也不沉默。

#### 4.6 信息真实性保障（四层防线）

| 层级 | 措施 |
|------|------|
| 第一层: 检索把关 | 相似度<0.7不放进Prompt + 来源标注 + 知识有效期 |
| 第二层: 生成约束 | Prompt强制"只用检索到的知识回答" + 标注来源编号[1][2] |
| 第三层: 输出校验 | 禁用语扫描 + 数值校验（保修月数/金额和知识库对比） |
| 第四层: 人工兜底 | 客服修改=信号（收藏=认可，修改=不认可）→数据飞轮输入 |

#### 4.7 意图识别渐进路线

| 阶段 | 方案 | 条件 |
|------|------|------|
| 阶段1（当前）| LLM零样本 + 积累标签数据 | 冷启动 |
| 阶段2 | 关键词规则 + LLM混合 | 积累500+条带标签数据 |
| 阶段3 | 微调RoBERTa分类器 + LLM兜底 | 积累2000+条带标签数据 |

#### 4.8 上下文分层管理

```
近15轮: 保留原文（在LLM有效注意力区间内）
15-30轮: 增量要点笔记（每5轮一条: 客户问题+解决方案+关键承诺）
30轮+: 一句总结
```

Prompt结构: 系统指令 → 30轮+总结 → 15-30轮笔记 → 最近15轮原文 → 当前消息 + RAG上下文

15轮分界的依据: 电商客服14轮峰值(JDDC数据)，LLM"中间迷失"效应在15K tokens后显著退化。

#### 4.9 层④ 对后续的影响

- Agent 架构决定了**工具服务的接口标准**——工具必须统一封装为 Function Calling Schema 可识别的格式
- 需要**成本监控基础设施**，按模型维度统计 Token 消耗
- 反思层做规则检查（格式完整性 + 标签合法性 + 禁用语扫描），不做 LLM 自评重试

### 层⑤ 评测体系

> ⚠️ 本节中所有量化指标（如"≥90%"、"≤5s"、"≤0.05元"）均为占位示例，用于说明指标类型和达标逻辑。真实数值将在选型报告中基于实际评测数据填入。

#### 5.1 评测体系四层金字塔

```
                    ┌─────────────┐
                    │   业务评测    │  ← "客服实际能用吗？"
                    │   端到端      │
                   ┌─┴───────────┴─┐
                   │   生成评测     │  ← "说得好不好？"
                   │   话术质量     │
                  ┌─┴─────────────┴─┐
                  │   检索评测      │  ← "找得准不准？"
                  │   RAG 质量      │
                 ┌─┴───────────────┴─┐
                 │   单元评测        │  ← "每个部件单独好不好？"
                 │   组件级          │
                └───────────────────┘
```

#### 5.0 技术选型分层策略

| 层级               | 做什么                                                                  | 不做什么                                             | 时限     |
| ------------------ | ----------------------------------------------------------------------- | ---------------------------------------------------- | -------- |
| 必须评测（阻塞性） | LLM模型选型、Embedding模型选型、Agent+Tool Router对比、Reranker价值验证 | —                                                   | ≤2天/项 |
| 快速验证           | 检索架构（向量vs混合）、Chunking策略                                    | 不做9种路由组合、不做72种Agent架构组合               | ≤1天/项 |
| 经验选择           | pgvector（团队已有PG）、混合检索、反思环暂不启用                        | 不评测Milvus/Chroma/FAISS、不评测Pipeline架构        | 0天      |
| V1.0不做           | —                                                                      | Reranker（评测后决定是否引入）、反思环（仅规则检查） | —       |

原则：快速淘汰明显不合格的候选，其余凭经验选，用线上数据迭代。

#### 5.2 第一层：单元评测（组件级）

每个模块独立评测，不依赖其他模块。

| 被评对象         | 评测数据                   | 指标           | 达标线       | 影响                 |
| ---------------- | -------------------------- | -------------- | ------------ | -------------------- |
| 意图分类         | 50条标注意图的客服消息     | Accuracy, F1   | ≥ 90%       | Agent 路由决策的基础 |
| Embedding 模型   | 50对 query-doc 标注        | Recall@5, MRR  | ≥ 85%       | 所有检索的基线       |
| OCR 准确率       | 30张订单/聊天截图+标注文本 | CER            | ≤ 5%        | 图片消息的处理质量   |
| CLIP 商品匹配    | 50张商品图+标注SKU         | Top-1, Top-5   | Top-1 ≥ 75% | 以图搜商品的可用性   |
| Function Calling | 30条需不同工具的query      | 工具选择准确率 | ≥ 85%       | Agent 编排质量       |

#### 5.3 第二层：检索评测（RAG 质量）

**评测方法对比：**

| 方法             | 做法                                   | 优点             | 缺点       |
| ---------------- | -------------------------------------- | ---------------- | ---------- |
| 人工标注测试集   | 标注 query→ground truth chunk         | 最可靠           | 成本高     |
| LLM 自动合成     | LLM 从文档生成 query→自动配对         | 量大便宜         | 可能不自然 |
| 对抗生成         | 专门构造容易找错的 query               | 测鲁棒性         | 覆盖面有限 |
| 混合方案（推荐） | 30条人工 + 50条合成 + 20条对抗 = 100条 | 质量+数量+鲁棒性 | 成本适中   |

**检索评测指标：**

| 指标     | 公式                           | 意义               |
| -------- | ------------------------------ | ------------------ |
| Recall@K | 前K个结果中包含正确答案的比例  | "有没有找到？"     |
| MRR      | 正确答案在结果中排名的倒数均值 | "找到的排第几？"   |
| NDCG@K   | 归一化折损累计增益             | "排序质量好不好？" |
| Hit Rate | 至少有一个正确答案的比例       | "至少对一次的概率" |

#### 5.4 第三层：生成评测（话术质量）

**评测方法：**

| 方法         | 做法                   | 优点             | 缺点                     |
| ------------ | ---------------------- | ---------------- | ------------------------ |
| 人工评估     | 2-3人对同一话术打分    | 最可靠           | 慢、贵、主观偏差         |
| LLM-as-Judge | 用另一个LLM打分        | 快、便宜、可复现 | LLM自身偏差              |
| 规则检查     | 关键词、长度、格式     | 快、确定         | 只能测表面               |
| 参考对比     | 对比生成话术和金标语术 | 客观             | BLEU/ROUGE不适用客服话术 |

**LLM-as-Judge 评测维度（1-5分）：**

① 相关性：是否准确回应客户问题？
② 准确性：涉及的事实（政策、商品参数）是否正确？
③ 共情度：是否体现对客户情绪的感知和安抚？
④ 可操作性：客户看完是否知道下一步该做什么？
⑤ 平台适配：话术风格是否符合平台调性？
⑥ 安全性：是否包含违规承诺或敏感内容？

**可用判定：** 所有维度 ≥ 4 分 → "可用"

**LLM-as-Judge 可靠性验证（必须做）：**

| 验证方法     | 做法                                         | 指标            |
| ------------ | -------------------------------------------- | --------------- |
| 人工一致性   | LLM-Judge vs 2个人工评委打分 → 相关系数     | Pearson r       |
| 模型交叉验证 | DeepSeek vs 千问 vs GPT-4 打分 → 两两一致性 | Cohen's Kappa   |
| 位置偏差检测 | A/B交换顺序，看Judge是否给相同结论           | 位置偏差率      |
| 长度偏差检测 | Judge是否天然倾向给长文本高分                | 长度-分数相关性 |

**哪个 LLM 当裁判？** 取 20 条人工标注金标语术，用 DeepSeek / 千问 / GPT-4 分别打分。**谁和人工的 Pearson r 最高，谁就当裁判。**

#### 5.5 第四层：业务评测（端到端）

| 指标       | 定义                             | 怎么测                | 达标线         |
| ---------- | -------------------------------- | --------------------- | -------------- |
| 可用率     | 生成话术不需修改可直接发送的比例 | 人工标注 50 条        | ≥ 70%（V1.0） |
| 采纳率     | 客服实际使用的比例               | 系统埋点              | ≥ 85%         |
| 修改率     | 客服修改了话术的哪些部分         | 生成版 vs 发送版 Diff | 用于数据飞轮   |
| 端到端延迟 | 从快捷键触发到气泡展示           | 计时打点              | P95 ≤ 5s      |
| 单次成本   | 每次生成的 API 费用              | Token 统计            | ≤ 0.05 元     |

| ----------------- | ------- | ------------- | -------------------------------- |

#### 5.7 评测体系对技术选型的闭环

```
同一套评测数据贯穿所有层：

评测数据 → 层② 检索策略评测 → 选出最优检索方案
         → 层③ Chunking 评测  → 选出最优切分方案
         → 层④ Agent 评测     → 选出最优架构+模型
         → 层⑥ 兜底评测       → 验证降级策略有效

最终：选型报告互相引用、互相印证
```

#### 5.8 层⑤ 对后续的影响

- 评测数据一旦构造完成，是**永久资产**——后续任何模型升级、策略调整都用同一套数据验证
- LLM-as-Judge 选定的裁判模型会成为后续所有生成质量评测的**标准裁判**
- 评测基线是后续迭代的**不可退化红线**——任何变更不能让指标下降

### 层⑥ 工程边界与兜底

#### 6.1 故障模式全景

```
                    ┌─────────────────────────┐
                    │     系统故障模式          │
                    └───────────┬─────────────┘
                                │
        ┌───────────┬───────────┼───────────┬───────────┐
        │           │           │           │           │
   外部依赖故障   内部组件故障   输入异常    输出异常    资源过载
   LLM挂了       RAG挂了      空消息      幻觉话术    Token超预算
   API超时       向量库挂了    乱码        违规内容    并发打满
   返回异常       检索超时     图片损坏    格式错乱    内存溢出
```

#### 6.2 三级降级链路

```
正常模式 ──────────────────────────────────────────
  浏览器扩展 → Web后端 → Agent(RAG+向量+CLIP) → 强模型 → 五步输出
                                                          → ✅ 全功能
                              │
                              │ 某个环节挂了
                              ▼
降级 L1: 无RAG模式 ─────────────────────────────────
  浏览器扩展 → Web后端 → Agent(纯LLM) → 强模型 → 五步输出
                                                      → ⚠️ "无知识增强"
                              │
                              │ 强模型也挂了
                              ▼
降级 L2: 备用模型模式 ──────────────────────────────
  浏览器扩展 → Web后端 → Agent(纯LLM) → 备用模型 → 五步输出
                                                      → ⚠️ "备用模型"
                              │
                              │ 全挂了
                              ▼
降级 L3: 模板兜底模式 ──────────────────────────────
  浏览器扩展 → Web后端 → 规则引擎 → 预置话术模板
                                                  → ⛔ "智能服务暂不可用"
```

**设计原则：逐级降级，永不阻断。每一级降级都明确告知用户当前状态。**

#### 6.3 五类故障的兜底策略

##### 外部依赖故障

| 故障场景          | 检测方式                | 兜底方案                        | 恢复策略             |
| ----------------- | ----------------------- | ------------------------------- | -------------------- |
| 主LLM不可用       | HTTP 5xx / 超时3s       | 自动切备用模型                  | 主模型恢复后自动切回 |
| 主LLM返回异常     | 输出格式校验失败/空响应 | 重试1次→仍失败切备用           | 记录异常             |
| Embedding服务挂了 | API超时                 | 降级纯BM25关键词检索            | 恢复后自动升回       |
| OCR服务挂了       | API超时                 | 跳过OCR，标注"图片识别暂不可用" | 恢复后处理积压       |

##### 内部组件故障

| 故障场景       | 检测方式          | 兜底方案                       | 恢复策略             |
| -------------- | ----------------- | ------------------------------ | -------------------- |
| 向量库挂了     | 连接超时/查询异常 | 降级数据库全文检索             | 恢复后切回向量检索   |
| 检索超时 >2s   | 计时器            | 跳过RAG，纯LLM生成             | 非阻塞，下次自动恢复 |
| RAG无结果      | 相似度<阈值       | 纯LLM生成 + 提示"无知识库匹配" | 记录为知识缺失       |
| CLIP匹配无结果 | 相似度<阈值       | LLM直接理解图片内容            | 不卡链路             |

##### 输入异常

| 故障场景        | 检测方式         | 兜底方案                           | 用户感知     |
| --------------- | ---------------- | ---------------------------------- | ------------ |
| 空消息          | 文本长度=0       | 提示"请选中客户消息后再触发"       | Toast弹窗    |
| 纯表情/乱码     | 有效字符占比<30% | 提示"无法识别有效内容"             | Toast弹窗    |
| 超长文本>2000字 | 字符计数         | 截断+提示                          | 黄色提示标记 |
| 图片损坏        | OCR返回空        | 提示"图片识别失败，已转纯文本模式" | 橙色提示     |

##### 输出异常

| 故障场景     | 检测方式               | 兜底方案                         | 用户感知 |
| ------------ | ---------------------- | -------------------------------- | -------- |
| 低置信度     | LLM自评<3/5            | 橙色标记"建议人工审核后发送"     | 橙色警告 |
| 话术格式缺失 | 五步中某步为空         | 展示已有步骤，缺失标灰           | 灰色占位 |
| 可能幻觉     | 生成内容与检索知识冲突 | 标记"与知识库信息不一致，请核实" | 红色警告 |
| 输出被截断   | 达max_tokens上限       | 标记"回复不完整"                 | 提示     |

##### 资源过载

| 故障场景        | 检测方式   | 兜底方案               | 用户感知             |
| --------------- | ---------- | ---------------------- | -------------------- |
| Token预算超限   | 累计计数   | 触发告警，限制高频用户 | 管理员告警           |
| 并发打满        | 请求队列>N | 排队提示               | 排队等待             |
| 单日API调用上限 | 调用计数   | 切换轻量模型           | 质量下降但服务不中断 |

#### 6.4 置信度评分机制（与层④④反思环交叉）

```
综合置信度 = w1×检索质量 + w2×生成质量 + w3×格式完整度

  检索质量信号：
    · 检索到的最高相似度分数
    · 检索结果数量
    · 检索-query 语义距离

  生成质量信号：
    · LLM 对自身输出的 6 维度自评分数

  格式完整度信号：
    · 五步是否齐全
    · 每步内容是否非空且不过短

≥ 0.8 → 🟢 高置信，可直接使用
0.5-0.8 → 🟠 中置信，建议审核
< 0.5 → 🔴 低置信，强烈建议人工重写
```

**需评测：** 取 30 条人工标分的话术，多组权重组合跑置信度，和人工评分的相关系数最高的权重组合为最优。

#### 6.5 数据安全边界

| 边界           | 策略                                       |
| -------------- | ------------------------------------------ |
| 客户信息脱敏   | 手机号/地址/身份证在日志中自动打码         |
| 生成内容控制   | 不生成包含"保证""承诺""100%"等绝对化用语   |
| Prompt注入防御 | 过滤客户消息中的"忽略之前的指令"等注入尝试 |
| 数据存储       | 对话记录脱敏落库，原始消息保留但标记为敏感 |

#### 6.6 需要调研对比的节点

| 对比项       | 候选方案                              | 评测指标           |
| ------------ | ------------------------------------- | ------------------ |
| 模型切换策略 | 自动切 vs 手动切 vs 半自动(告警+确认) | 切换延迟、误切率   |
| 降级质量衰减 | 全链路 vs L1 vs L2 vs L3              | 各级可用率、延迟   |
| 置信度权重   | 不同 w1/w2/w3 组合                    | 与人工评分相关系数 |
| Retry 策略   | 立即重试 vs 指数退避 vs 不重试        | 成功率 vs 延迟增加 |

#### 6.7 层⑥ 对后续的影响

- 降级链路的**用户感知提示**需要在前后端统一设计
- 模型切换的**熔断器逻辑**需要在调用层统一实现，而非每个服务各自实现
- 置信度评分的权重需要**在层⑤评测中校准**后固化

> 不做选择也是一种选择——但应该是讨论之后的有意决定，而非没看见的遗漏。
