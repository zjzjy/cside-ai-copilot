## 2 产品定位

### 2.1 产品定义

CSide 是面向电商代运营场景的浏览器侧边栏 AI 客服助手。产品以**五步生成法**为核心方法，把一次客服沟通拆解为意图识别、回复策略、推荐话术、钩子引导、成功收尾五个环节，逐环节给出可审核、可发送的建议，帮助客服在售前咨询中推动客户完成下单。

产品的输入是单条客户消息与当前店铺上下文，输出是结构化的五步建议及其知识依据。系统不提供自动发送能力，回复内容由客服确认后发送。

### 2.2 核心理念

**把不可复制的个人经验，变成可共享的团队能力。** 资深客服对客户意图的判断、对沟通节奏的把握、对促成时机的选择，长期只存在于个人身上。通过五步协议把这一过程结构化，新人可以直接复用，团队整体水平随之抬升。

**赋能而非替代。** AI 的角色是"带教学的副驾驶"：既生成话术，也把背后的策略逻辑展示出来，客服在使用中理解"为什么这样说"。决策权与发送权始终在客服手中。

**跨平台一致。** 无论客服在淘宝、京东、拼多多还是抖音后台操作，面对的是同一套话术体系、同一套操作方式、同一个知识库，不需要为不同平台记不同规则。

### 2.3 目标用户与角色

表 2-1 用户角色与能力

| 角色 | 定义 | 核心诉求 | 系统提供的能力 |

## 3 业务分析

### 3.1 业务背景

代运营公司的客服岗位与品牌自营客服有本质区别：一名客服人员往往同时负责多个品牌、多个平台和多个店铺。本方案规划覆盖的品牌包括 vivo、华为、OPPO、小米，店铺上下文共 6 个，平台范围包括淘宝与天猫、京东、拼多多、抖音。

这种矩阵式分工带来两个直接后果。一是会话上下文高频切换，客服上一分钟还在处理某品牌淘宝店的咨询，下一分钟可能已切到另一品牌京东店；二是每个品牌、每个店铺的退货政策、保修范围、促销活动和话术口径各不相同，需要记忆的信息量远超个人经验所能承载的范围。

结果是回复质量高度依赖个人经验：资深客服能凭经验快速判断客户诉求、把握政策边界、顺势推动下单；新人则容易答非所问、做出超范围承诺，或把问题答完就结束对话。人员一旦流动，这些经验也随之流失。

### 3.2 三大核心痛点

电商客服行业存在三个结构性矛盾，且相互叠加。产品选择聚焦这三个，因为它们正是本产品形态（外部工具、浏览器侧边栏、人机协同）能够最直接解决的。

**痛点一：质量鸿沟**

表 3-1 质量鸿沟

| 维度 | 说明 |
|---|---|
| 现象 | 同一店铺内，资深客服与新人面对同类咨询，转化效果差距明显；生硬的机器人式应答答非所问，反而损害客户体验 |
| 根因 | 优质话术与判断力存在于资深客服个人身上，无法复制；新人成长依赖师徒带教，周期长、成效不确定 |
| 产品应对 | 五步生成法把资深客服的思维过程产品化（意图→策略→话术→引导→收尾）；知识检索让每句话术都有商品信息与政策条款作为事实依据；话术库让个人经验沉淀为团队资产 |

**痛点二：效率瓶颈**

表 3-2 效率瓶颈

| 维度 | 说明 |
|---|---|
| 现象 | 首次响应时间过长会显著提高客户流失；大促期间咨询量成倍增长，临时扩充人力导致服务质量下滑 |
| 根因 | 客服的核心工时消耗在"想怎么回复"上：查商品信息、翻政策条款、斟酌措辞。这部分时间无法通过简单压缩解决，因为回复质量不能牺牲 |
| 产品应对 | 一次生成五步结构，把查资料、想策略、组织语言合并为一个动作；客服只需审核与复制，决策权保留在人手中 |

**痛点三：经验流失**

表 3-3 经验流失

| 维度 | 说明 |
|---|---|
| 现象 | 电商客服岗位人员流动率长期偏高。一名资深客服离职，其积累的优质话术、典型案例与产品理解随之流失 |
| 根因 | 行业普遍缺少知识沉淀机制。对话记录停留在聊天日志中，无人整理、无人标注、无人复用，每次人员流动都是一次知识资产损失 |
| 产品应对 | 五步数据协议把每条对话结构化留存（客户消息、意图、检索知识、生成话术、实际发送话术）；分步收藏带标签进入话术库；沉淀结果同时服务团队复用与后续模型优化 |

本节引用的转化差距、首响流失率、人员流动率等数值为行业参考值，须在立项阶段以企业自有数据校准。

### 3.3 痛点选择说明

客服行业还有两类常被提及的问题：人力成本高、被动咨询不转化。

前者需要平台接口能力才能解决，而本产品的定位是提升人效而非减少编制，不在本方案的能力范围内。

后者虽然重要，但本质上被质量鸿沟覆盖：话术质量提升、回复中自带钩子引导环节之后，转化会随之改善。因此转化目标不作为独立痛点展开，而是作为质量鸿沟被解决后的直接结果，落实为第 2.4 节的产品目标之一。

转化提升的实现路径也由此明确：售前沟通中，客户往往已经具备购买意愿，缺少的只是临门一脚的推动。五步中的钩子引导环节专门承担这一职责，把"推动客户进入下一步"从可做可不做的个人习惯，变成每次生成都必须给出的必答项。

## 4 核心方法：五步生成法

### 4.1 设计出发点

售前咨询的价值不在于把客户的问题答完，而在于把客户带到下单。传统客服话术体系通常只覆盖"回答问题"这一层，既缺少对客户所处阶段的判断，也缺少推动客户进入下一步的动作。这正是咨询量很大、成交率却上不去的直接原因：客服答得没错，但客户没有被推动。

五步生成法的设计出发点，就是把这套判断与推动的过程显性化、结构化，让每一次生成都必须走完从识别到推动的完整链条。

### 4.2 五步定义

表 4-1 五步定义与对客服的价值

| 步骤 | 名称 | 内容 | 对客服的价值 | 在转化中的作用 |
|---|---|---|---|---|
| 第一步 | 意图识别 | 解析客户诉求、情绪与隐藏需求 | 我理解了客户想要什么 | 判断客户所处决策阶段，为后续策略提供依据 |
| 第二步 | 回复策略 | 问题解决与情绪安抚的双重逻辑 | 我应该用什么策略回应 | 决定采用信息解答、价值锚定、异议化解还是临门推动 |
| 第三步 | 推荐话术 | 平台适配、可直接复用的完整脚本 | 我具体说什么 | 承载说服内容，是客户实际看到的信息 |
| 第四步 | 钩子引导 | 挖掘客户利益点，推动下单或复购决策 | 我怎么促成下一步 | **转化发生的关键环节**，把客户带到下单、加购、领券或查看详情 |
| 第五步 | 成功收尾 | 构建良好体验，铺垫复购转化 | 我怎么让客户满意地结束 | 关闭本次沟通，为复购与后续触达留出接口 |

### 4.3 五步与客户决策路径的对应

图 4-1 客户决策路径与五步的对应关系

```
客户决策路径                    五步生成法的对应产出

信息了解 ─┐
方案比较 ─┼─▶ 第一步 意图识别：判断所处阶段、情绪与隐藏需求
异议处理 ─┤
决策临门 ─┘
                    │
                    ▼
             第二步 回复策略：匹配该阶段的说服路径
                    │
                    ▼
             第三步 推荐话术：输出可发送的说服内容
                    │
                    ▼
             第四步 钩子引导：推动进入下单等下一步动作  ◀── 转化关键点
                    │
                    ▼
             第五步 成功收尾：关闭本次沟通并铺垫复购
```

### 4.4 五步生成法的双重身份

五步生成法在产品中承担两重角色，短期价值与长期价值各不相同。

**短期身份：质量控制工具。** 确保每次生成都覆盖五个关键要素，避免出现"只给答案不给策略""只解决问题不做转化"这类常见缺失。五个环节可逐项校验，缺项即可判定生成无效并重新生成。

**长期身份：数据标注协议。** 每一步都是一次结构化的数据产出。一条对话留存后即为一条训练数据，包含客户原始消息、意图分析、检索到的知识、模型生成的话术与客服实际发送的话术；客服对生成内容的每一次修改都是人类偏好信号。这些数据积累到一定规模后，可用于训练更贴合代运营场景的专属模型。

双重身份决定了产品的一个关键设计：**执行引擎可以替换，输出协议保持不变。** 生成能力会从多模型调用逐步演进到检索增强乃至专属模型，而五步的数据格式始终稳定，积累的数据不会因引擎升级而失效。

### 4.5 为什么采用五步，而不是直接输出一段话

表 4-2 五步生成法与自由文本对比

| 维度 | 自由文本 | 五步生成法 |
|---|---|---|
| 可校验 | 只能判断内容是否通顺，无法判断是否遗漏关键环节 | 逐步校验，字段缺失或长度不足即判定本次生成无效并重新生成 |
| 可定位 | 客服只能整段重写 | 客服可明确知道问题出在策略、话术还是引导环节，按步调整 |
| 可沉淀 | 收藏的是一段话，缺少上下文 | 每一步独立标注，按步骤进入不同用途的沉淀库 |
| 可度量 | 只能统计使用次数，无法判断转化贡献 | 可分别统计采纳率与引导执行率，定位转化瓶颈所在环节 |
| 对促成的影响 | 模型倾向只回答问题，引导动作常被省略 | 引导动作成为必答字段，从机制上避免遗漏促成 |

## 5 业务流程

### 5.1 现状流程

图 5-1 现状业务流程

```
客户发起售前咨询
  → 客服依据个人经验回答问题
  → 是否引导客户下单取决于个人习惯与经验
  → 客户在咨询结束后自行决定，部分客户流失
  → 优质促成话术留存于个人工作记录，未纳入团队知识
  → 同类咨询在新增人员中重复出现，转化水平难以提升
```

该流程的核心问题是经验未被结构化承载，促成动作未被约束，导致质量不可复制、转化不可度量。

### 5.2 目标流程

图 5-2 目标业务流程

```
客户发起售前咨询
  → 客服在电商后台选中消息，使用快捷键抓取
  → 侧边栏识别品牌、平台与店铺上下文，客服确认
  → 系统基于当前店铺知识生成五步建议，其中包含下一步引导动作
  → 侧边栏展示本次引用的知识来源
  → 客服审核与调整，复制推荐话术并发送，按建议执行引导
  → 客户进入下单等下一步动作，完成转化
  → 客服对优质内容分步收藏，进入团队话术资产
  → 运营管理员维护品牌与店铺配置，持续优化转化口径
```

### 5.3 业务规则

表 5-1 核心业务规则

| 编号 | 规则 | 说明 |
|---|---|---|
| BR-1 | 五步完整性 | 单次生成必须完整产出五个环节，任一环节缺失或长度不足即视为无效 |
| BR-2 | 三级知识体系 | 知识分为通用层、品牌层与店铺层，检索时按层级加权合并 |
| BR-3 | 品牌隔离 | 非通用层的知识必须与请求品牌一致，否则不予采用 |
| BR-4 | 禁用语双重约束 | 命中品牌禁用语的知识不参与生成；禁用语同时写入生成约束 |
| BR-5 | 三级规则配置 | 品牌配置、平台政策、店铺配置共同生效，品牌差异优先 |
| BR-6 | 上下文完整性 | 品牌、平台、店铺任一未确认时，不得发起生成 |
| BR-7 | 输入长度限制 | 客户消息长度不得超过 500 字符 |
| BR-8 | 人工发送 | 系统不提供自动发送能力，回复由客服确认后发送 |
| BR-9 | 收藏即沉淀 | 客服收藏的分步内容自动带标签进入话术资产库，无需额外标注动作 |

## 6 产品方案

### 6.1 产品形态与运行环境

表 6-1 产品形态

| 形态 | 技术实现 | 定位 |
|---|---|---|
| 浏览器侧边栏 | Chrome Extension Manifest V3、Side Panel API、React 19、TypeScript | 客服端主操作界面 |
| 管理后台 | React 19、TypeScript、Vite、Ant Design 5 | 配置入口 |
| 后端服务 | Spring Boot 4.0.3、JDK 21 | 业务处理与能力编排 |
| 数据层 | PostgreSQL 17、pgvector、Redis 7 | 数据存储与向量检索 |

运行环境要求 JDK 21、Node.js 20 LTS、Docker Desktop，浏览器为 Chrome 或 Edge 116 及以上版本。

选择侧边栏作为主要形态，是因为客服的工作现场就在电商后台：侧边栏常驻右侧无需切屏，不遮挡会话与商品信息，且能直接获取页面选中的客户消息和店铺地址。计算密集的检索与生成在后端完成，侧边栏专注交互与展示。

### 6.2 总体设计

五步生成法是产品的核心，三条支撑主线共同保证其准确与可用。

图 6-1 总体设计

```
核心：五步生成法
  意图识别 → 回复策略 → 推荐话术 → 钩子引导 → 成功收尾

支撑主线一 上下文正确
  侧边栏随平台标签页自动识别品牌、平台与店铺
  自动识别结果仅作为候选，须经人工确认后方可生成
  切换店铺时清空历史结果，生成返回后再次校验上下文一致性

支撑主线二 知识正确
  三级知识体系：通用层 → 品牌层 → 店铺层
  混合检索：中文 BM25 关键词检索与向量语义检索融合，并按层级加权
  强约束：跨品牌知识不予采用，命中品牌禁用语的知识不参与生成

支撑主线三 闭环沉淀
  知识溯源展示、分步收藏、品牌与店铺配置、转化效果度量
```

### 6.3 技术架构

表 6-2 技术架构与实现选型

| 层次 | 实现 | 说明 |
|---|---|---|
| 大语言模型 | 兼容 OpenAI 接口的多供应商降级链 | 主用 DeepSeek，备选通义千问与腾讯混元，按配置顺序切换 |
| 向量模型 | 本地部署 BGE 或云端嵌入服务，维度统一为 1024 | 两套实现可切换，共用同一向量列 |
| 检索 | 中文 BM25 与 pgvector 余弦相似度混合排序 | 兼顾关键词精确匹配与语义泛化 |
| 鉴权 | JWT 无状态认证 | 有效期 24 小时 |
| 数据 | PostgreSQL 与 pgvector，JSONB 承载扩展字段 | 支持配置与元数据的灵活演进 |

模型参数、检索权重与数据契约详见《CSide AI 产品需求文档》第 5 章与附录。

### 6.4 关键设计决策

表 6-3 关键设计决策与依据

| 编号 | 决策事项 | 方案选择 | 依据 |
|---|---|---|---|
| D1 | 核心方法 | 五步生成法 | 售前转化取决于是否完成从识别到推动的完整链条；结构化方法可保证环节不被遗漏，也便于度量各环节的转化贡献 |
| D2 | 引擎与协议的关系 | 引擎可替换，协议保持稳定 | 生成能力会持续演进，但已积累的数据必须跨版本可用；把协议与引擎解耦，长期数据资产不会因技术升级而失效 |
| D3 | 交互形态 | 浏览器侧边栏 | 客服工作现场位于电商后台，侧边栏可避免切换应用，并可直接获取页面选中文本与店铺上下文 |
| D4 | 上下文处理 | 自动识别并强制人工确认 | 多店铺并行是常态，跨店错配属于最高风险场景；未确认时禁止生成，以一次点击的成本规避业务事故 |
| D5 | 输出形式 | 结构化五步协议 | 结构化输出可校验、可定位、可沉淀、可度量，优于自由文本 |
| D6 | 知识组织 | 通用、品牌、店铺三级继承 | 与代运营业务的知识分布一致，兼顾复用效率与品牌隔离要求 |
| D7 | 检索方案 | 关键词与向量混合检索 | 客服问题包含大量型号与政策关键词，需精确匹配；同时存在口语化表达，需要语义泛化 |
| D8 | 模型策略 | 多供应商降级链 | 外部接口存在波动风险，单一供应商故障将使全部客服不可用 |
| D9 | 生成参数 | 低温度采样 | 客服话术需要稳定可复现，低温可降低措辞漂移与内容编造 |
| D10 | 责任边界 | 人工审核后发送 | 错误承诺与违规表述的业务代价高，产品定位为辅助工具 |
| D11 | 数据资产 | 收藏即沉淀 | 客服的收藏行为自带场景标签，无需额外标注成本即可积累高质量样本 |

## 7 产品流程

### 7.1 系统交互总览

图 7-1 系统交互总览

```
浏览器侧边栏 ──HTTP/JWT──▶ 后端服务 ──SQL──▶ PostgreSQL + pgvector
                              │
                              ├──▶ 向量服务（本地 BGE 或云端嵌入服务）
                              └──▶ 大语言模型降级链

管理后台 ──HTTP/JWT──▶ 后端服务（品牌配置、店铺配置）
```

### 7.2 话术生成流程

图 7-2 话术生成流程

```
1. 客服输入或抓取客户消息
2. 侧边栏校验：消息非空、长度不超过 500 字符、上下文已确认
3. 客户端发起生成请求，携带客户消息与店铺上下文
4. 后端解析用户、品牌配置、平台政策与店铺信息
5. 执行知识检索：召回候选，完成品牌隔离与禁用语过滤，混合排序取前 5 条
6. 构建提示词并调用大语言模型，按五步结构生成，执行降级与格式校验
7. 解析五步结果，写入会话与消息记录
8. 返回结果，侧边栏二次校验上下文一致性后展示
9. 客服复制推荐话术并发送，按钩子引导推动客户进入下一步动作
```

### 7.3 店铺上下文识别与切换

图 7-3 上下文识别与切换流程

```
页面加载、地址变化或定时轮询
  → 依据域名识别平台，依据地址参数与页面标题识别品牌
  → 生成候选上下文，来源标记为自动识别，确认状态为未确认
  → 通过后台服务按标签页隔离存储，并推送至侧边栏
  → 客服确认或手动选择后，来源标记为手动，确认状态为已确认
  → 切换上下文时清空客户消息、生成结果、收藏状态与会话标识
```

### 7.4 分步收藏

图 7-4 分步收藏流程

```
客服对五步中的任一步执行收藏
  → 后端依据会话反查品牌、平台与店铺，自动完成标注
  → 写入收藏记录，包含步骤类型、内容、客户消息与标签
  → 按步骤类型进入不同的资产用途，详见第 9 章
  → 支持按品牌、步骤类型分页查询
```

### 7.5 知识库初始化

图 7-5 知识库初始化流程

```
服务启动或手动触发
  → 遍历知识库种子数据
  → 依据目录判定知识层级与类型
  → 生成 1024 维向量，向量生成失败时保留文本内容
  → 依据来源标识幂等写入，批量提交
```

### 7.6 配置生效

图 7-6 配置生效流程

```
管理员修改品牌配置
  → 后端更新品牌配置记录
  → 后续生成同时作用于两处：提示词中的禁用语约束与检索阶段的禁用语过滤
  → 配置即时生效，无需重启服务或重新导入知识
```

## 9 数据飞轮

### 9.1 收藏即沉淀

产品在三个痛点之上贯穿一条长期主线：客服的每一次收藏，都在为团队的知识库与未来的专属模型积累素材。

机制上遵循一条简单规则：**客服收藏的内容直接视为可用资产与后续训练的初筛结果。** 产品不对数据设置多层级的价值判定（不区分修改幅度、修改者身份等维度），因为这类规则既难以可靠执行，也会显著增加客服的操作负担。收藏动作本身已经包含"这条有价值"的判断，这一条规则足够清晰且可落地。后续如需人工精筛，是对已收藏数据的二次过滤，不影响基础机制。

### 9.2 分步收藏的去向

五步的每一步被收藏后，进入不同的资产用途。

表 9-1 分步收藏去向

| 收藏的步骤 | 沉淀分类 | 后续用途 |
|---|---|---|
| 第一步 意图识别 | 意图案例库 | 用于验证与补充意图识别评测集 |
| 第二步 回复策略 | 策略模式库 | 按场景与意图分类，遇到同类场景可直接复用策略逻辑 |
| 第三步 推荐话术 | 话术模板库 | 可直接复用的话术；高频内容可进入检索候选池 |
| 第四步 钩子引导 | 引导模板库 | 按平台与场景分类，跨对话复用，直接服务转化 |
| 第五步 成功收尾 | 收尾模板库 | 按场景分类复用 |

收藏时系统自动标注品牌、平台、场景与客户原始消息，客服无需手工填写任何标签。

### 9.3 演进路径

表 9-2 数据飞轮三阶段

| 阶段 | 对应版本 | 主要动作 | 目标 |
|---|---|---|---|
| 冷启动期 | V1.0 | 种子知识导入；首批资深客服持续产出并收藏话术；跑通生成链路 | 积累第一批经过验证的结构化数据 |
| 积累期 | V1.5 | 收藏数据持续汇入；引入人工精筛做质量把关 | 积累足够数据，启动首轮模型优化实验 |
| 飞轮期 | V2.0 | 更高质量的生成带来更高收藏率，收藏继续反哺数据 | 形成正向循环，模型始终作为辅助工具，决策权与发送权在人手中 |

### 9.4 长期价值

界面可以被模仿，模型可以被采购，但长期沉淀的垂直场景数据无法被复制。**真正形成差异的不是模型本身，而是资深客服在日常使用中持续沉淀的高质量结构化对话数据。** 这也是五步协议必须在引擎升级过程中保持稳定的根本原因。

## 10 指标体系

指标体系按结果、过程、质量、效率四层组织。结果层衡量五步生成法对成交的实际贡献，过程层定位转化在哪个环节出现损耗，质量层守住合规底线，效率层保障客服能够及时使用。

表 10-1 产品指标体系

| 层次 | 指标 | 定义 | 目标 |
|---|---|---|---|
| 结果 | 售前咨询下单率 | 产生下单行为的售前咨询会话数与售前咨询会话总数之比 | 相较基线提升 |
| 结果 | 咨询到下单转化率 | 售前咨询会话中完成下单的比例，按品牌与店铺拆分 | 相较基线提升，且各店铺无显著下滑 |
| 结果 | 接待人转化差异 | 不同客服之间售前下单率的离散程度 | 差异收窄，体现能力可复制 |
| 过程 | 五步生成采纳率 | 复制推荐话术次数与生成成功次数之比 | 建立基线并持续提升 |
| 过程 | 引导执行率 | 客服保留并执行钩子引导的比例 | 建立基线；该环节是转化关键点 |
| 过程 | 五步完整率 | 返回结果中五步字段均满足长度要求的比例 | 不低于 95% |
| 过程 | 分步收藏量 | 累计收藏各步骤内容的条数 | 建立基线 |
| 质量 | 禁用语命中率 | 生成文本中包含品牌禁用语的请求占比 | 0，为强制要求 |
| 质量 | 跨品牌知识返回数 | 返回知识中品牌与请求品牌不一致的条数 | 0，为强制要求 |
| 质量 | 政策口径错误投诉 | 因生成建议导致的口径类投诉数量 | 不上升，为强制要求 |
| 效率 | 生成延迟 | 请求发起到结果返回的耗时，统计 P50 与 P95 | P50 不高于 6 秒，P95 不高于 20 秒 |
| 效率 | 单条回复耗时 | 从抓取客户消息到完成发送的总时长 | 相较现状下降 |

结果层指标依赖订单数据与会话数据的关联，需在订单数据接入后启用；在此之前，以过程层指标衡量产品使用深度。相关安排见第 13 章。

## 11 产品边界与合规要求

### 11.1 产品强制约束

表 11-1 产品强制约束

| 编号 | 约束 |
|---|---|
| C-1 | 系统不得提供自动向客户发送消息的能力 |
| C-2 | 系统不得主动读取或存储完整聊天记录 |
| C-3 | 涉及优惠、保修、退换等内容须以知识库为准；缺少依据时应引导客服确认后再回复 |
| C-4 | 生成内容须标注为参考建议，发送前由客服人员核对 |
| C-5 | 检索结果不得包含非当前品牌的私有知识 |
| C-6 | 生成内容不得包含当前品牌的禁用语 |
| C-7 | 引导动作须在店铺政策允许范围内提出，不得作出超出政策的承诺 |

### 11.2 合规与安全要求

表 11-2 合规与安全要求

| 事项 | 要求 |
|---|---|
| 个人信息保护 | 客户消息仅用于本次生成与必要的会话留存，不用于与产品功能无关的用途 |
| 数据留存 | 会话与收藏数据的保留期限须符合企业制度与平台规则 |
| 访问控制 | 服务接口须校验访问令牌，管理后台的配置变更须限定为授权角色 |
| 密钥管理 | 模型与数据库密钥须通过环境变量注入，不得写入代码仓库 |
| 浏览器权限 | 扩展仅申请必要权限，域名访问范围限定为受支持的电商平台 |
| 内容责任 | 生成结果为辅助建议，业务责任由使用方的审核环节承担 |

## 12 风险与应对

表 12-1 风险清单

| 编号 | 等级 | 风险描述 | 影响 | 应对措施 |
|---|---|---|---|---|
| R-1 | 高 | 店铺标识在不同系统间口径不一致 | 店铺层知识可能无法被检索，促销与售后场景缺少依据 | 统一标识规则，在知识元数据中固化店铺字段，并建立标识映射关系 |
| R-2 | 高 | 转化数据依赖订单与会话的关联 | 订单数据接入前，下单率无法量化 | 优先完成订单数据关联，明确统计口径后启用结果层指标 |
| R-3 | 中 | 禁用语过滤针对知识整条内容 | 命中禁用语时可能连带丢弃有效知识 | 改为命中词汇的脱敏替换或降权处理 |
| R-4 | 中 | 店铺维度的权限控制 | 多租户接入后存在越权访问可能 | 建立店铺授权模型与接口级鉴权 |
| R-5 | 中 | 收藏标注依赖会话上下文 | 缺少上下文时标签可能不准确 | 缺少上下文时拒绝写入或要求显式传入 |
| R-6 | 中 | 密钥管理 | 密钥泄露将导致越权访问 | 通过环境变量注入并定期轮换 |
| R-7 | 中 | 引导内容的执行依赖客服 | 转化关键环节可能未落地 | 在侧边栏突出引导内容，并将引导执行率纳入日常监控 |
| R-8 | 低 | 平台政策的注入形式 | 影响提示词可读性与生成质量 | 转换为自然语言文本后注入 |

## 13 演进规划

### 13.1 规划原则

按能力成熟度分阶段推进：先构建核心链路并沉淀数据，再建立转化度量体系，随后扩展权限与转化能力，最后按投入产出比评估能力扩展。

### 13.2 版本规划

表 13-1 演进规划

| 版本 | 主题 | 主要范围 | 目标 |
|---|---|---|---|
| V1.0 | 核心链路 | 五步生成法；三级知识体系与混合检索；店铺上下文识别与生成门禁；分步收藏；品牌与店铺配置管理 | 跑通核心链路，产出第一批结构化沉淀数据 |
| V1.5 | 转化度量与权限 | 订单与会话数据关联；过程与结果指标埋点；店铺授权模型与接口级鉴权；评测集自动回归 | 可量化五步生成法对下单率的贡献，支持多租户接入 |
| V2.0 | 转化能力增强 | 意图识别结合历史转化数据；按决策阶段输出差异化引导；优质引导自动进入知识库；个人话术库与分步调整 | 提升引导执行率与整体转化 |
| V3.0 | 能力扩展 | 多轮上下文管理；多模态输入；转化看板与知识缺口识别 | 按投入产出比评估后实施 |

图 13-1 演进路线

```
V1.0 核心链路  →  V1.5 转化度量与权限  →  V2.0 转化能力增强  →  V3.0 能力扩展
```
