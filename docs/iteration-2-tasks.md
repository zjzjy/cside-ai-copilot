## 一、交互缺失补齐（3项）

### IT2-01: 侧边栏对话历史

**现状**: 侧边栏只有当前消息的五步生成区，无历史对话浏览能力。

**目标**: 客服打开侧边栏 → 看到当前店铺的对话列表 → 点进某个对话 → 查看完整多轮消息 + 对应五步。

**详细设计**:

- 对话列表：每项显示客户第一句话摘要 + 消息条数 + 最后活跃时间 + 状态标签（进行中/已结束）
- 点进对话：上区为可滚动的多轮对话（客户/客服一来一回），下区显示当前选中轮次的五步结果
- 点击历史某条消息 → 五步区域切换到该轮的五步结果
- 可输入新消息继续该对话
- 后端已有 `GET /api/v1/conversations/{id}`，需补 `GET /api/v1/conversations?store_id=xxx` 列表接口

**实现范围**:

- [ ] 后端: 新增 `GET /api/v1/conversations` 列表接口（按 store_id 筛选 + 分页）
- [ ] 前端扩展: 对话列表组件 + 对话详情视图（多轮消息 + 五步切换）
- [ ] 前端扩展: Side Panel 入口改为对话列表（作为默认视图）

## 二、Agent 架构升级（8项）

### IT2-04: 意图识别渐进路线实现

**现状**: 五步法 Step1 纯 LLM 零样本判断意图，无结构化分类。

**目标**: 实现渐进升级路线的基础设施，支持从 LLM 零样本 → 关键词+LLM混合 → 微调分类器的平滑过渡。

**详细设计**:

- 阶段1（当前）: LLM 零样本，同时将每次 Step1 的输出 + 原始消息存入 `intent_labels` 表（为后续阶段积累数据）
- 阶段2（500+条后）: 高频意图配置关键词规则，匹配不上才调 LLM
- 阶段3（2000+条后）: 微调 RoBERTa 分类器做主力，LLM 兜底低置信度 case

**实现范围**:

- [ ] 后端: 新建 `intent_labels` 表（customer_message, intent_output, confidence, created_at）
- [ ] 后端: 每次五步生成时自动写入意图标签数据
- [ ] 后端: 管理后台增加"意图分类规则"配置接口（为阶段2准备）

---

### IT2-05: 上下文分层管理

**现状**: 多轮对话上下文全部塞进 Prompt，无截断和摘要策略。

**目标**: 实现分层拼接——近15轮保留原文，15-30轮用增量要点笔记，30轮+用一句总结。

**详细设计**:

- 近15轮: 原文完整保留（在 LLM 有效注意力区间内）
- 15-30轮: 每5轮生成一条要点笔记（客户问题+解决方案+关键承诺）
- 30轮+: 整个对话压缩为一句话总结
- Prompt 结构: 系统指令 → 30轮+总结 → 15-30轮笔记 → 最近15轮原文 → 当前消息 + RAG 上下文

**实现范围**:

- [ ] 后端: 上下文构建服务（ContextBuilder），按轮次分层拼接
- [ ] 后端: 要点笔记生成逻辑（复用现有 LLM，额外字段输出）
- [ ] 后端: 对话轮次计数器

### IT2-06: 长期记忆 — 知识缺失自发现

**现状**: RAG 检索不到时无感知，知识缺口无法被发现。

**目标**: 自动检测检索失败 → 语义聚类 → 累计推送 → 管理员审核入库。

**详细设计**:

- 触发条件: RAG Top-1 相似度 <0.7 AND LLM 自判 `knowledge_sufficient: false`
- 语义聚类: 相似查询归为一类（Embedding 余弦相似度 >0.7）
- 推送阈值: 同类查询累计 ≥5 次 → 管理后台"待补充知识清单"
- LLM 自判: 五步生成时额外输出 `knowledge_sufficient: true/false`（零额外调用成本）
- 管理员审核周期: 每周一次

**实现范围**:

- [ ] 后端: 新建 `knowledge_gaps` 表（query_cluster_id, representative_query, occurrence_count, rag_scores, detected_at）
- [ ] 后端: 检索日志记录服务（每次 RAG 检索记录 query + Top-K 分数）
- [ ] 后端: 语义聚类服务（定时 Job，聚类低分查询）
- [ ] 后端: LLM 五步输出新增 `knowledge_sufficient` 字段
- [ ] 前端管理后台: "待补充知识清单"页面 + 编辑入库

### IT2-07: 长期记忆 — 店铺趋势感知

**现状**: 同类问题短期内高频出现无预警。

**目标**: 管理后台展示异常趋势预警——突增检测 + 持续高位检测。

**详细设计**:

- 突增检测: 今日某问题次数 > 过去7日均值 × 2
- 持续高位: 本周某问题次数 > 过去4周均值 × 1.5
- 只做后台预警展示，不注入 Prompt
- 按店铺/品牌维度独立统计

**实现范围**:

- [ ] 后端: 新建 `trend_alerts` 表
- [ ] 后端: 趋势计算定时 Job（每日/每周）
- [ ] 前端管理后台: "趋势预警"页面

### IT2-08: Tool Router（Orchestrator 模式）

**现状**: MVP 单 Agent 直接生成五步，工具调用流程写死。

**目标**: 采用 Orchestrator 模式——LLM 自主决策调哪些工具、什么顺序，一次调用完成路由+生成。

**详细设计**:

- 架构: Orchestrator 模式（非 Router，非 Semantic Router）
- 8 个工具: search_product / search_policy / search_faq / search_script / search_image / understand_image / resolve_link / understand_video
- 工具全为只读检索（无需状态机双轨架构）
- CSide 不必用大企业的"状态机+LLM"双轨——工具少+只读+人工兜底
- 业界共识: Function Calling 在 ≤10 个工具时表现优秀

**实现范围**:

- [ ] 后端: 8 个工具统一封装为 Function Calling Schema
- [ ] 后端: Orchestrator Agent 服务（单次 LLM 调用：路由决策 + 并行工具调用 + 五步生成）
- [ ] 后端: 工具注册与发现机制

### IT2-09: 输入全景路由

**现状**: 只处理文字输入。

**目标**: 支持四种输入类型的自动识别和路由。

**详细设计**:

| 输入类型      | 处理方式                                   |
| ------------- | ------------------------------------------ |
| 文字          | 意图识别 → Tool Router → RAG → 五步生成 |
| 图片-以图搜图 | CLIP 匹配商品库 → 注入商品信息            |
| 图片-内容理解 | 多模态 LLM 直接理解 → 合并到消息          |
| HTTP 链接     | 解析商品 ID → ERP API 查商品              |
| 视频          | 多模态 LLM 理解 → 合并到消息              |

图片路径判断: 多模态 LLM 一次调用同时完成"判断类型"和"处理内容"。

**实现范围**:

- [ ] 后端: 输入类型检测中间件
- [ ] 后端: 链接解析器（淘宝/京东/拼多多/抖音 URL → 商品ID）
- [ ] 后端: 多模态 LLM 调用封装（图片理解 + 视频理解）

### IT2-10: 工具失败三级降级

**现状**: 工具调用失败无优雅降级。

**目标**: 三级降级链确保永远有响应。

**详细设计**:

- Level 1: 跳过失败工具 → 用其他可用工具继续 → 告知"XX信息暂时获取不到"
- Level 2: 所有检索挂 → 纯 LLM 兜底 → 标注"⚠️未检索到实时信息，仅供参考"
- Level 3: LLM 也挂 → 固定话术"暂无法处理，建议联系人工"
- 核心原则: 永远给客服一个响应，宁可降级也不沉默

**实现范围**:

- [ ] 后端: 工具调用失败分类（超时/限流/网络/服务端错误）
- [ ] 后端: 重试策略（指数退避，最多3次）
- [ ] 后端: 降级链编排服务
- [ ] 后端: 故障日志记录

### IT2-11: 信息真实性四层防线

**现状**: 无系统化的信息真实性保障机制。

**目标**: 检索→生成→校验→人工四层防幻觉体系。

**详细设计**:

| 层级             | 措施                                               |
| ---------------- | -------------------------------------------------- |
| 第一层: 检索把关 | 相似度<0.7不放进Prompt + 来源标注 + 知识有效期     |
| 第二层: 生成约束 | Prompt强制"只用检索知识回答" + 标注来源编号[1][2]  |
| 第三层: 输出校验 | 禁用语扫描 + 数值校验（保修月数/金额和知识库对比） |
| 第四层: 人工兜底 | 客服修改=不认可信号 → 数据飞轮输入                |

**实现范围**:

- [ ] 后端: 检索结果评分过滤（<0.7 丢弃）
- [ ] 后端: Prompt 模板更新（来源标注指令）
- [ ] 后端: 禁用语扫描器（品牌禁用语表）
- [ ] 后端: 数值校验器（提取话术中数字 → 对比知识库）

## 三、P1 业务增强（3项）

### IT2-12: 级联重生成

**现状**: `POST /api/v1/generate` 一次性生成全部五步，无编辑后重生成能力。

**目标**: 按 SRS §9.1.1 规则实现级联重生成。

**详细设计**:

- 改 Step1 → Step1/2/3/4/5 全部重生成
- 改 Step2 → Step2/3/4/5 重生成
- 改 Step3 → Step3/4/5 重生成
- 改 Step4 → Step4/5 重生成
- 改 Step5 → 仅 Step5 重生成

交互约束: 修改后绿色边框（已锁定）+ 下游灰色骨架屏 + 点"应用修改"后触发
LLM入参: 被修改步内容 + 客户原始消息 + 已检索知识 + 上游未变步骤

**实现范围**:

- [ ] 后端: 新增 `POST /api/v1/generate/regenerate` 接口
- [ ] 前端扩展: 五步编辑框（每步可编辑）
- [ ] 前端扩展: 级联重生成交互（绿色锁定 + 灰色骨架屏 + 应用修改按钮）

### IT2-13: 链接→商品映射

**现状**: 客户消息中的商品链接无法自动解析。

**目标**: 解析各电商平台商品链接 → 通过 ERP API 查询商品信息 → 注入上下文。

**详细设计**:

- 支持平台: 淘宝/京东/拼多多/抖音商品链接
- 解析方式: 从 URL 提取商品 ID（如淘宝 `id=xxxxx`）
- 数据源: **迭代二自建模拟数据**——项目内维护一套示例商品数据（JSON文件或数据库种子数据），包含 vivo/OPPO/小米 等品牌的商品信息（SKU、名称、价格、图片URL、描述），覆盖淘宝/京东/拼多多/抖音四种链接格式。后续版本替换为真实ERP连接
- 如模拟数据查不到: 降级为提示"未找到该商品信息"

**实现范围**:

- [ ] 后端: URL 解析器（4个平台）
- [ ] 后端: 链接-商品映射表 + 示例种子数据（自建，覆盖3品牌×4平台）
- [ ] 后端: 降级处理（查不到时）

### IT2-14: CLIP 以图搜商品 + 商品图片库

**现状**: 无图片搜索能力。

**目标**: 客户发商品照片 → CLIP 向量匹配 → 返回最相似的商品。

**详细设计**:

- CLIP 服务: **Jina CLIP v2 API**（中文友好 + 免费100万token/月）
- 图片向量库: pgvector **独立表** `product_images`（768维 CLIP 向量，与文字向量库分表）
- 元数据: 商品图片URL、CLIP向量、商品SKU、品牌、品类、商品名称、商品描述
- 离线管道: 自建图片种子数据 → Jina CLIP v2生成向量 → 写入 pgvector
- 在线查询: 客服收到图片 → Jina CLIP v2生成查询向量 → pgvector检索Top-K → 返回商品信息
- 图片来源: **迭代二自建模拟数据**——准备10-20张示例商品图片（覆盖 vivo/OPPO/小米 的典型产品），手动放入项目 resources 目录，作为种子数据写入 product_images 表

**实现范围**:

- [ ] 后端: `product_images` 表（含 pgvector 768维 HNSW 索引）
- [ ] 后端: Jina CLIP v2 API 对接层
- [ ] 后端: 图片种子数据导入脚本（从 resources 目录读取示例图片→Jina CLIP v2生成向量→写入product_images表）
- [ ] 后端: 以图搜商品接口 `POST /api/v1/search/image`

## 五、基础设施（横切关注点）

### IT2-17: 多店铺知识库权限隔离

**现状**: 后端 RAG 检索搜所有店铺的知识库，无权限过滤。

**目标**: 根据客服的店铺授权范围过滤检索结果。

**详细设计**:

- JWT 中新增 `store_ids` 字段（客服被授权的店铺列表）
- pgvector 查询: `WHERE store_id IN (jwt.store_ids)`
- 品牌/通用知识过滤: 按客服负责的品牌范围
- 管理后台: 客服-店铺分配页面

**规模验证**: 500品牌×2500店铺×810条/店 ≈ 200万向量，单客服检索仅搜约6000条（0.3%），pgvector HNSW p50<5ms。离 pgvector 5000万上限差两个数量级。

**实现范围**:

- [ ] 后端: JWT 扩展（store_ids 字段）
- [ ] 后端: RAG 检索权限过滤器（WHERE store_id IN）
- [ ] 前端管理后台: 客服-店铺分配配置页面

### 7.2 各库详细信息

#### 1. 商品知识库

- **Chunk策略**: 按SKU分块，每块=一个商品的完整信息（规格+卖点+参数）
- **更新频率**: 自建种子数据（迭代二为手动触发）
- **权限**: 按店铺隔离（store_id IN 授权列表）
- **RAG检索权重**: 高

#### 2. 商品图片库

- **向量维度**: CLIP 768维（与文字库1024维分开，不同空间不能混合检索）
- **离线管道**: 自建种子数据→下载图片→Jina CLIP v2 API生成向量→写入pgvector
- **在线查询**: 客服收到图片→Jina CLIP v2生成查询向量→pgvector HNSW检索Top-5
- **更新频率**: 自建种子数据时批量更新
- **权限**: 按品牌/店铺过滤

#### 3. 政策规则库

- **内容**: 平台退货政策 + 品牌保修条款 + 法律底线规则 + 店铺特殊规则
- **继承逻辑**: 店铺→品牌→平台→法律 四级叠加
- **更新频率**: 政策变更时管理员手动更新
- **检索方式**: 混合检索（向量 + BM25关键词）

#### 4. FAQ语料库

- **内容来源**: 管理员录入 + IT2-06知识缺失自发现推送
- **检索权重**: 中等（多路召回中的一条路径，非前置拦截）
- **更新频率**: 管理员审核后入库（每周一次）
- **特殊机制**: 知识缺失自发现自动推送待补充FAQ

#### 5. 话术模板库

- **内容来源**: 客服收藏Step3推荐话术自动入库
- **分类**: 按步骤类型(1-5)、品牌、平台自动打标签
- **检索权重**: 低（辅助参考，非主要信息来源）
- **数据飞轮**: 收藏即初筛——高频收藏的话术自动提升检索权重

#### 6. 媒体素材库

- **内容类型**: 安装视频链接、故障对照图片、使用指南
- **检索方式**: 通过图片/视频的"文字描述"做向量检索（图片和视频本身不做向量化）
- **客服使用**: RAG检索到后，客服可复制链接发给客户
- **存储**: 图片/视频文件存对象存储，pgvector只存URL+文字描述+向量

#### 7. 链接-商品映射

- **映射逻辑**: URL中的平台+商品ID → 查自建映射表 → 返回SKU+商品信息
- **支持平台**: 淘宝(`id=`)、京东(`sku=`)、拼多多、抖音
- **自建数据**: 迭代二在项目中维护一套示例映射（覆盖3品牌×4平台，共12条商品链接），JSON文件或数据库种子数据
- **降级**: 模拟数据查不到 → 返回提示

#### 8/9. 品牌/店铺配置

- **已有功能**: MVP V1.0 已完成 CRUD
- **迭代二变更**: 店铺配置新增"分配给客服"多选（配合IT2-17权限隔离）

| ------------------ | ----------------------------------------------------------------- | --------------------------------------- |
